# コミット規約

## 目的

後から履歴を追う人が「なぜその変更を行ったのか」を理解できるように、コミットメッセージの書き方を統一します。`commit-msg` フックによる機械検証を通過することを前提とします。

---

## フォーマット仕様

### 1. 件名（1行目）

- **通常コミット**: `[{scope}]{type}: {日本語の概要}`
  - `{scope}`: 影響範囲（例: `[repo]`, `[frontend]`, `[packages]`, `[shared]`）
  - `{type}`: `feat` / `fix` / `refactor` / `docs` / `chore`
  - ※ ADR（設計決定記録）を追加する場合は、末尾に `#ADR` を付けます（例: `[repo]docs: 認証方式の選定 #ADR`）。
- **マージコミット**: `{branch} をマージ: {日本語の概要}`
  - ブランチ名と「をマージ」の間に半角スペースを入れます。
- **概要の書き方**:
  - 何をしたかを1文で簡潔に書きます（終止形または体言止め）。
  - 末尾に句点（。）は付けません。

### 2. 本文の構成

本文は差分から読み取れない「背景」「理由」「振る舞いの変化」を書きます。箇条書きではなく**散文**で記述し、以下の見出しを順序通りに使用してください。

#### 通常コミット
```markdown
## 背景
変更前の状態、観測した課題や動機。

## 方針
採用した解決策とその理由、あえて見送った代替案。

## 効果・影響
利用側から見た振る舞いや体験の変化。
```

#### マージコミット
```markdown
## サマリー
マージの目的と達成された状態。

## 含まれる変更
振る舞い単位の主な変更内容。

## 残課題
マージ後に残る作業や今後の対応。
```

---

## 記述・文体ルール

- **長さ**: 全体（件名含む）で **600文字以内** に収めます。
- **改行と句点**:
  - 本文は **1文1行** で書き、文末は必ず **句点（。）** で終えます。
  - 見出し（`#`）、空行、コードブロック内、表行（`|`）の末尾には句点を付けません。
- **文と文の接続**:
  - 因果関係は文を分けずに接続表現（「〜のため」「〜ことから」）でつなぎます。「〜のためである。」といった独立文は避けてください。
- **補足情報の書き方**:
  - 文末の括弧による後置補足は避け、文の中に自然に組み込みます。
    - ×: `tags`パラメータを追加した（CSV形式、最大10件）。
    - ◯: `tags`パラメータをCSV形式で最大10件まで受け付けるようにした。
- **効果・影響の視点**:
  - 実装の内部数値ではなく、利用側（ユーザーや外部システム）から観測できる変化を書きます。
- **用語**:
  - 識別子や固有名詞を除き、英単語の混在を避けて平易な日本語で書きます。
  - 言及する外部リポジトリは公開リポジトリのみとします。

## メッセージの例（通常コミット）

```markdown
[api]fix: リクエストボディをzodで検証し、不正な入力を400で拒否する

## 背景

これまで`POST /todos`はリクエストボディを型アサーションで信頼して処理しており、`title`の欠落や空文字でもそのまま保存できてしまっていた。
入力チェックはフロント側にしかなく、APIを直接呼び出すクライアントからの不正な入力は素通りしていた。

## 方針

不正な入力を防ぐため、リクエストボディをzodのスキーマで検証し、違反時はエラー詳細付きの400を返すようにした。
バリデーションロジックの重複を避けるため、各ハンドラではなく`createTodo`の入口で一括検証している。

## 効果・影響

`POST /todos`は不正なリクエストを400 Bad Requestで拒否し、不正データがDBに登録されなくなった。
正常系リクエストへのレスポンス仕様は変わらないため、フロント側の変更は不要である。
```

## 作業手順（エージェント向け）

1. **事実の確認**:
   - 背景や方針は、ユーザーの指示とコード差分から確認できる事実のみで構成します。
   - 意図を推測で補う必要がある場合は、コミット前に必ずユーザーへ確認を取ってください。
2. **下書きの作成**:
   - 一時ディレクトリに下書きファイル（`commit-draft-{title}.md`）を作成します。
3. **コミットの実行**:
   - `git commit -F <下書きファイルのパス>` でコミットします。
   - コミット完了後、下書きファイルを削除します。
4. **フックエラー時の対応**:
   - `commit-msg` フックで弾かれた場合は、フック側ではなくコミットメッセージ側を修正して再実行します。

---

## 環境設定（参考）

- リポジトリ作成時は、実行権限を付与した `templates/commit-msg` を `.githooks/commit-msg` に配置し、`git config core.hooksPath .githooks` で有効化します。
- フックの内容は全リポジトリで統一し、規約変更時はテンプレート側を修正して各リポジトリへ反映します。
