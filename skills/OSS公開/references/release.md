# リリース

公開後は、変更のまとまりごとに版を切り、タグとGitHub Releaseを作る。

## 版とタグ

- 版数はリポジトリのマニフェストを唯一の正とし、リリースのたびに上げる（例：`package.json`の`version`、.NETは`.csproj`の`Version`）。
- タグは`v{version}`の注釈付きタグにし、マニフェストの版数と一致させ、リリース対象のcommitを指すようにする。
- READMEの導入コマンドには版数やタグを含めない。
  Bunのgit依存は`#semver:`の範囲を解決できず、版を書くとリリースごとにREADMEを直すことになるためである。
  再現性は利用側のlockfileが担い、版を固定したい利用者はタグを`#v{version}`で指定できる。

## リリースノート

リリースノートは、その版へ更新する利用者が「自分に関係する変更」を短時間で把握するためのものであり、commitログの写しではない。

- 読者はリポジトリの内部構造を知らない利用者であり、本文には外から観測できる変化を書く。
- 言語は日本語にし、リポジトリが別の言語を既定としている場合だけその言語に合わせる。
- 材料は前回のタグから`HEAD`までのcommitとし、各commitの「背景」と「効果・影響」から利用者が観測する変化を抜き出す。
- commitの件名や本文はそのまま貼らない。
  GitHubが自動生成するノートは下書きにだけ使う。
- 利用者に影響する依存更新は載せる。
- 利用者の行動を変えない変更（内部のリファクタ、テスト、ドキュメント、ロゴ）は載せない。

### 構成

- 冒頭は`『{サブタイトル}』をリリース！`の定型行にする。
  サブタイトルは、その版の特徴を短く遊び心をもって表す。
- 続けて、その版の要点を伝える導入を置く。
  個人が管理するリポジトリでは、Discordのリリースノートのように遊び心のある調子を基本とする。
- 導入のあとに注意書きを置いてよい。
  破壊的変更があるときは最後の「⚠️ 破壊的変更」へ案内し、重要なセキュリティ修正があるときはその存在に触れる。
- 変更は「🎉 新機能」「🐛 不具合修正」「⚠️ 破壊的変更」の見出しで分け、該当がある見出しだけを置く。
- 「🎉 新機能」には、新しくできるようになったことと、前より扱いやすくなったことを入れる。
- 「🐛 不具合修正」には、期待どおり動かなかった点とセキュリティの修正を入れる。
- 「⚠️ 破壊的変更」には、利用者が行動を求められる変更（機能の削除、既定値の変更、対応環境の引き上げ、非推奨化）をまとめる。
- 各項目は一文で、利用者から見た変化を書く。
  関連するcommitやissueへのリンクは任意とし、リンクが無くても意味が通るように書く。

```markdown
『{サブタイトル}』をリリース！

{その版の要点を伝える導入}
{必要な場合だけ、破壊的変更や重要なセキュリティ修正への注意書き}

### 🎉 新機能
- {新しくできるようになったこと、扱いやすくなったこと}

### 🐛 不具合修正
- {直った不具合、セキュリティ修正}

### ⚠️ 破壊的変更
- {利用者が対応を求められる変更}
```
