# アーカイブを作る

## 試行ディレクトリ

- 試行の題材ごとに、分かりやすい名前のディレクトリを作る。
- **汎用の規則はこのスキルに置き、題材でだけ決まることは題材ディレクトリの `AGENTS.md` に書く。**
  - 題材の `AGENTS.md` には、目的、用語、入力を置く場所、ビルドのコマンド、原本を残すかどうかなど、その題材固有のことを書く。
  - 記録は題材ディレクトリの `記録.md` に置く。
- 作業中は中身が散らかっていてよい。区切りで1つのHTMLにまとめる。

## 何を残すか

1つの自己完結HTMLに、次をすべて内包する。基準は「何を試し、何が分かったかを振り返れ、必要ならソースで方法を追えるか」とする。

| 含める | 役割 |
|---|---|
| 記録 | 何を試し、何が分かり、どう判断したか |
| 図（成果物） | 到達点を一目で分かるようにする |
| 素材 | ソース・入力・テーマ・生データなど、方法を追うためのもの |

取得済みライブラリ、配布バイナリ、フォント、lockfile、生成サイト、反復した出力、網羅的なログや測定データは置かない。HTMLとソースから内容を読み取れるためである。

## 構成の方針

順序の意味は「読むためか、残すためか」だけである。厳密な順序は固定しない。

- **前（読むため）**：記録と図。並びは書き手が決めてよい。図を先頭にする題材も、条件や目的を先頭にする題材もよい。
- **後（残すため）**：素材。折りたたみで末尾にまとめ、読者の邪魔をしない。
- 説明書は、節の名前や順に依存せず、本筋（記録）の位置をidで指す。

## 作る

- 単一HTMLで完結させる。画像・図も埋め込み、外部のファイルやURL、フォントを参照しない。
- 描画は上流の `article-preview` CLI に任せる。入力記法の正はCLI側のスキルであり、ここには書かない。`--media inline` で画像をdata URIにする。
- **記録は生のMarkdownのコードブロック**としてそのまま置く。見出しを展開しない。記録のh1はタイトルに使う。アーカイブは記録の見出し名に依存しない。
- **図**は `<Image zoom>` で内包する。PNGは表示に足りる大きさのWebP（品質80）にする。
- **素材**はファイルごとに畳んだサブセクション（`### > パス`）で置く。
- 読者エージェント向けの**説明書**を `archive-guide` のdata blockに1つだけ埋め込む。
- ファイル名に「アーカイブ」を含める。1つの題材につき1ファイルとする。
- **作業用の中間ファイルはリポジトリに残さない**（/tmp を使う）。
- 原本を別に残すか、内包だけにするかは題材の `AGENTS.md` に従う。

雛形は `templates/build-archive.py`。作業場所へコピーし、上部の規約を題材に合わせて直して使う。

```sh
ARTICLE_PREVIEW='article-preview' python3 build-archive.py <試行ディレクトリ>
```

## 説明書

作成者が読者エージェント向けに、読む順と重要な箇所をidで書く。`templates/説明書.md` を出発点にする。画面には表示しない。`build-archive.py --guide` で渡し、省略時は節構成から生成する。

## 記録の書き方

段階ごとに書く。`templates/経過と記録.md` を出発点にする。

- 段階ごとに、何を試し、何が分かり、どう判断したかを書く。
- 確認できる記録・ログ・会話に基づいて書く。
- 当時の意図や判断は、記録に書かれている範囲にとどめる。
- ユーザーの評価は、そのときの言葉のまま残す。
- 不明な点は不明なまま書く。
- 整理で新たに分かったことは、当時の検証結果と区別して書く。
- 判断の根拠に必要な箇所だけを書く。ソースの写しにしない。

## 点検

- [ ] 単一HTMLで、外部のファイル・URL・フォントを参照していない
- [ ] 記録が生のMarkdownのコードブロックで入っている
- [ ] 図と記録が前、素材が後ろに畳んである
- [ ] 説明書が `archive-guide` に1つだけある
- [ ] 試行ディレクトリの全ファイルが内包されている（取込漏れの検査が通った）
- [ ] h1が1つ
- [ ] 秘密情報が入っていない

画像生成で案を作った場合は、[画像生成によるデザインの試行錯誤](imagegen-design.md)も読む。
