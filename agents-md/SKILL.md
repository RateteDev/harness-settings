# エージェント指示書

`AGENTS.md` だけをエージェント指示書の正本とする。適用範囲の異なる指示は、その範囲に対応する `AGENTS.md` へ置き、同じ規則を複製しない。

OpenCode はグローバルと現在位置から上位にある `AGENTS.md` を継続的な指示として読み、読み取り先の下位ディレクトリにある `AGENTS.md` も必要になった時点で追加する。この性質に見合う内容だけを置くことが、本スキルの原則である。

## 言語と文体

日本語で書く。自然言語の規則は、所有者が読み返して直さなければ腐敗を止められず、所有者が監査する文書だからである。コード識別子・パス・固有名詞は原語のまま書く。

文体は、所有者が一読して意味を取れることを基準にする。

- 段落は「課題 → 例 → 帰結」を接続詞でつなぎ、論理を追える文章にする。文を切りすぎて箇条書きを地の文へ並べた形にしない。
- 後置修飾を重ねない。「〜した〜が〜する〜」の形になったら、修飾を前に出すか文を分ける。
- 比喩・擬人化・警句を書かず、事実と帰結を平叙文で書く。指示書では印象より理解速度を優先する。
- 表のセルでも主語を省かない。
- 英語の既存文書から移す場合も直訳せず、日本語で書き直す。

## 置き場の振り分け

判断軸は「誰が、いつ読むか」の一つである。`AGENTS.md` は適用範囲内で常時読む場所なので、それ以外の読まれ方で足りる内容は該当する場所へ置く。

| 内容 | 置き場 | 理由 |
|---|---|---|
| 何を作っているか、誰のためか、判断の前提となる背景 | 適用範囲の `AGENTS.md` | あらゆる判断の分母として常時必要 |
| ソースを読んでも分からない制約 | 適用範囲の `AGENTS.md` | 機械が止めない誤りを止めるため。下記「制約とは」を参照 |
| 破ると被害が大きい行動ルール | 適用範囲の `AGENTS.md` | 行動前に常時参照できる必要がある |
| 特定の関数・ファイルを触る時だけ必要な理由 | その実装の隣のコメント | 触る瞬間だけ必要で、全セッションに不要 |
| 特定の作業をする時だけ必要な規則 | その作業を扱うスキル | スキルの description だけが常時見え、本体は該当作業で読み込まれる |
| 特定のディレクトリを触る時だけ必要な規則 | そのディレクトリ直下の `AGENTS.md` | 下位の指示は、その範囲を読んだ時点で追加される |
| 特定の操作の瞬間だけ必要な手順 | フックなどの動的な指示注入 | ディレクトリで切れないツール名やコマンドを条件にできる |
| コマンドとその説明 | タスクランナーのレシピと doc コメント | コマンド一覧が発見面であり、写しは古くなる |
| 決定の経緯・没案・捨てたもの | ADR またはコミット本文 | 決定時点の記録で、現在の規則とは寿命が異なる |
| 未決事項 | コード側の `TODO(slug)` | 検索結果を一覧として使える |
| ディレクトリ構成・サービス配置の写し | 書かない | `ls` と各設定ファイルが正本であり、写しはドリフトする |
| 他文書の内容や役割の説明 | 書かずに必要なパスだけ示す | 相手の文書が変わった時に説明が古くなる |
| 進捗・作業ログ | 書かない | 常時読む価値がない |
| より広い範囲の `AGENTS.md` と同じ規則 | 書かない | 広い範囲の正本を直した時に古い版が残る |

一つの規則は一箇所にだけ置く。動的な注入へ寄せた規則を `AGENTS.md` やファイル先頭コメントへ重ねず、スキルへ寄せた規則も `AGENTS.md` に再掲しない。

### 制約とは

「構成の写し」と「構成への制約」は、ソースを読めば分かるか否かで区別する。

写しは `ls` やタスクランナーの一覧、設定ファイルから復元できる情報なので書かない。制約は、現在のソースがたまたま満たしているだけで、次の変更が破ってもコンパイルやテストが止めない「あってはならない形」なので書く。

- `{module-a}` は `{module-b}` を import してはならない — import がない現状だけでは、禁止か未実装かを区別できない
- `{value}` の正本は `{config-file}`。他のスクリプトに直書きしない — 直書きしても現在値と一致すれば検査を通る
- プロセスマネージャがサーバーを所有する。手動起動の代わりに管理コマンドを使う — プロセスの所有関係はソースだけでは分からない
- `{layer}` は `{value}` を計算せず、渡された値だけを表示する — 計算を追加しても動くため、責務の境界を別途示す必要がある

## 章構成

動機から規則へ進む順に書く。問題と前提を先に読ませると、規則をその帰結として理解できる。

| 章 | 答える問い | 書くもの |
|---|---|---|
| 起きていた問題 | なぜこれを作るのか。何が困っていたか | 作る前の状態。何を試し、具体的にどこで困ったか。製品名・項目名を挙げる |
| 解決するための方針 | どの方向から解くのか | 何を軸に据えるか。問題章の不満を裏返した指針 |
| このリポジトリでの前提 | 方針を成立させる、コードに現れない条件は何か | 利用者の数、公開範囲と時期、復元の要否、開発フェーズ、所有関係 |
| インフラ・運用に関するコンテキスト | リポジトリの外に何があるか | このマシンとリポジトリ外にある状態。表で書く |
| 常時遵守するべき制約 | 前提から導かれる規則は何か | ソースを読んでも分からない「あってはならない形」と、破ると被害が出る行動。表で書く |

章は固定する。h1 の直下に要約文を置かず、空にする章があっても章を増やしたり並べ替えたりしない。読み手が「どこに何があるか」を覚えなくてよい状態を保つ。

「起きていた問題」は製品ビジョンを問題の形に言い換えない。「{理想の状態} がなかった」ではなく、「{既存の製品} を試したら {具体的な不満} があった」という実際の起点を書く。理想の状態は方針章に置く。

### インフラ・運用の章の境界

この章は「構成の写しを書かない」規則の例外である。書くのは、リポジトリの中を読んでも分からないマシン側とリポジトリ外の状態だけとする。

登録済みのユニット、ビルド済みのイメージ、データディレクトリ、秘密の置き場、外部到達経路、物理端末の入力などを扱う。ソースを読めば分かる実装関係や、単一ファイルが語るポート番号・環境変数値・イメージ名は写さず、どのファイルが正本かを書く。

| 構成要素 | 状態 | 正となる定義 |
|---|---|---|
| `{unit-or-container}` | このマシンで常駐。データはリポジトリ外の `{location}` | `{unit-file-or-compose}` |
| 秘密 | リポジトリ固有のものは `{app-secret-location}`、共通のものは `{shared-secret-location}` 経由 | `{env-example}`、`{shared-secret-location}` |

## 一項目の書き方

制約は **規則 | 理由** の 2 列の表で書く。箇条書きは積まれるほど読みにくくなるが、表は列がそろうため一覧できる。

理由のない禁止は「今回は例外だろう」と判断される。理由があれば、当てはまらない場面では正しく無視され、当てはまる場面では守られる。理由が一文で成立すれば、過去の出来事を添える必要はない。

| 規則 | 理由 |
|---|---|
| `{対象}` の変更後は `just {restart-recipe}` を実行し、サーバーを手で起動・停止しない | 対象は起動時にしか読み込まれず、手動起動した複製はプロセスマネージャ配下のプロセスとポートを取り合う |

理由が一文で書けない規則は、前提章に不足がある。理由を長くせず、前提を足す。

否定形には代替を添える。「{手段} を使わない」だけでは、必要が生じた時に別の手段が発明される。

別文書を読ませる必要がある場合は、パスと「いつ読むか」を平文で書く。特定クライアントだけが解釈するインポート構文には依存しない。

## 作成と全面改稿の手順

`AGENTS.md` を新規作成する時、および既存ファイルを章構成ごと書き直す時は、次の順で進める。

1. **ソースと履歴を先に読む。** インフラ表と制約表に書く事実（登録済みユニット、イメージ、データや秘密の所在、外部到達経路、既存規則が生まれたコミット）は、所有者へ尋ねる前に確認する。
2. **所有者へヒアリングする。** 問題・方針・前提はソースや履歴だけで確定できない。既存の `AGENTS.md` や README から推測せず、質問ごとに「現在の記載」と「疑う理由」を添え、所有者が一つずつ否定できる形で確認する。
3. **書く。** ヒアリングの回答とソースの確認結果から、`templates/AGENTS.md` に沿って全文を書く。既存文書を直訳しない。
4. **検査する。** `references/checklist.md` を別のサブエージェントに渡し、書き方とソースとの一致を判定させる。問題・方針・前提の事実としての正しさは、所有者が読んで判断する。

既存文書が英語で書かれている場合は、内容を無条件に信用せず、ソース確認とヒアリングをやり直す。

## 検査

既存の `AGENTS.md` が規約に沿っているかは、`references/checklist.md` をサブエージェントに渡して判定させる。書き方に加えて、インフラ表と制約表はソースと突き合わせる。問題・方針・前提の妥当性は所有者にしか判断できないため、所有者にも読んでもらう。

サブエージェントへの渡し方:

- 主エージェントはチェックリストの中身を読まず、検査観点を独立させる。
- サブエージェントが絶対パスを読める場合は、チェックリストの絶対パスだけを渡し、内容を書き写さない。権限がない場合に限り、ファイル内容を加工せずに指示へ含める。
- 対象の `AGENTS.md`、適用される上位の `AGENTS.md`、タスクランナーのコマンド一覧、利用可能な各 `SKILL.md` もパスまたはコマンドとして渡す。
- 返答は「行 → 観点 → 直し方」の表だけを求め、修正はさせない。

## 追加と削除の運用

追加の契機は、エージェントが誤った瞬間とする。破られた実績のない規則を先回りして増やさない。

削除の契機は理由が消えた時とする。廃止したサービス向けの規則や、修正済みの不具合への注意書きは、その変更と同時に消す。

編集のたびに各項目へ「この適用範囲で常時読む必要があるか」と問い、実装側コメント・スキル・動的な注入・タスクランナー・ADR へ移せるものは移す。

## 新規リポジトリでの配置

`templates/AGENTS.md` を対象リポジトリへ配置し、作成手順に従って埋める。雛形は骨組みだけを持ち、定型の規約文を持たない。空欄を埋めただけで内容を検討したと誤認させないためである。

中身の当否は機械的な文面比較ではなく、本スキルの検査手順に従って所有者と別のサブエージェントが確認する。
