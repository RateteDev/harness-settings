# Gemini推敲

スキルの文書の言い回しを、Geminiに読みやすく直させるための手順である。
ユーザーが求めた場合だけ使う。

Geminiの書き直しは読みやすくなる一方で、規則の強さや対象の範囲を変えてしまうことがある。
書き直しは差分で確かめられる形で行い、意味の変化を元に戻してから残す。

## あるべき状態

- 書き直した文書は、元の規則と意味を保ち、言い回しだけを読みやすくする。
- frontmatterは書き直さず、元のまま残す。
- 書き直した文書も、[スキルの書き方](skill-writing.md)の規約を満たすようにする。
- 1ファイルの書き直しと手直しを1コミットにまとめ、ファイルごとに履歴を追えるようにする。

## 守る順序

1. 対象のファイルをコミットしてから、スクリプトに通す。
   スクリプトは未コミットの変更があるファイルを受け付けない。
   差分をGeminiの書き直しだけにし、`git restore`で戻せるようにするためである。
2. `git diff`で差分を読み、規則の意味が変わった箇所を元に戻す。
   特に次の変化を探す。
   - 規則の強さの変化：「設定を意図どおりにする」が「意図どおりであることを確かめる」になる、「推奨」が消える。
   - 対象の範囲の変化：「〜だけ」「〜の場合だけ」のような限定が消える。
   - 理由の脱落：例外扱いされやすい規則に添えた理由が消える。
3. 見出しの構成、あるべき状態の文末、一文一行、強調の閉じ方を、スキルの書き方の規約に合わせて直す。
4. ファイルごとにコミットする。
   本文には、Geminiで書き直したことと、元に戻した箇所を書く。

意味の変化を確かめる前にコミットすると、変わった規則が正しい履歴として残り、後から差分を読み直さないと見つけられなくなる。

## 手段

- 書き直しは`bun scripts/gemini-rewrite.ts <ファイル>...`で行う。
  使い方は`--help`で確かめる。
- APIキーは環境変数`GEMINI_API_KEY`で渡す。
- モデルとシステムプロンプトはスクリプトの先頭で固定している。
  変えるときは、同じファイルを旧設定と新設定の両方で書き直し、出力を比べてから変える。
