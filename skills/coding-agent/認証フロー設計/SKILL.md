# 認証フロー設計

## このスキルの目的

パスキーとGoogleサインインが互いの予備になる最小の認証にそろえる。
パスワードと回復コードをなくし画面の説明文と遷移を減らす。

## 認証手段

パスキーとGoogleサインインの2つだけを使う。
Sign in with AppleはiOSアプリで[審査ガイドライン4.8](https://developer.apple.com/app-store/review/guidelines/#login-services)に求められたときだけ加える。
方針と食い違う要望は設計の前に指摘し次の理由を示して合意を取る。

| 採らない手段 | 理由 |
|---|---|
| メールのOTPとリンク | パスキーと並べるとアカウントの強さがフィッシングに弱いメールの水準まで下がる |
| Sign in with Apple | iPhoneの利用者はパスキーで同じ手軽さを得られWebでも有料の開発者登録が要る |
| 認証アプリ | パスキーが単独で2要素を満たしスマホと一緒に失われやすい |
| パスワードと回復コード | 漏えいとフィッシングに弱く回復は残った手段で足りる |

## アカウントと連絡先メール

連絡先メールは連絡と通知だけに使いサインインにも回復にも使わない。
確認コードもメールの所有を確かめるためだけに使う。
メールの確認はその場で求め確認が済むまでサービスを使わせない。

確認済みのメールは複数のアカウントで重複させない。
確認したメールが既存のアカウントと同じなら新しく作らず既存の手段でサインインして連携するよう案内する。
メールが同じでもアカウントを自動で統合しない。

## 登録

ログインなしで使えるサービスは価値を体験させてから登録を促す。
Googleの経路は連絡先メールの確認が済むまで仮登録とする。
パスキーの経路はパスキーを作った時点で本登録とし仮登録を作らない。

## ログイン

前回のログイン方法はブラウザに手段の種類だけを残し名前やメールは残さない。

## 回復と手段の管理

回復専用の流れは作らず残った手段でサインインして登録し直させる。
全ての手段を失うと復旧できないことを設定画面に書き手段が1つの利用者には予備の登録を促す。

手段の追加・削除とメールの変更の前には再認証させる。
最後の1つの手段は削除させない。
手段を変えたら他の端末のセッションを切り連絡先メールへ通知する。

## 画面

画面と遷移は[認証の体験](examples/認証の体験.html)に従う。
Googleとパスキーの確認画面はGoogleとOSが出すため作らない。
HTMLがブラウザに保存しているアカウントはサーバーの代わりである。
HTMLにない画面の文言とアイコンは[Passkey Central](https://www.passkeycentral.org/design-user-journeys/principles)に従う。
