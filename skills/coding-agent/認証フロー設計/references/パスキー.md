# パスキー

パスキーの登録・サインイン・管理を実装・レビューするときに読む。
連絡先メールの確認と重複の扱いは`連絡先メール.md`に従う。

## ライブラリ

- サーバーは`@simplewebauthn/server`、ブラウザは`@simplewebauthn/browser`を使う。
- `@simplewebauthn/server`はCloudflare Workersへの対応を明記していないが、v14.1.0は`node:`の読み込みを持たず`globalThis.crypto`だけを使うため、採用前にWorkersで登録とサインインが通ることを試す。

## 登録のオプション

| 項目 | 値 | 理由 |
|---|---|---|
| `rp.id` | サービスの登録可能なドメイン | サブドメインをまたいで同じパスキーを使うため |
| `user.id` | アカウントごとの32バイトの乱数 | 変わらない値にし、メールなどの個人情報を含めない |
| `user.name`・`user.displayName` | 「サービス名と作成日」の仮の名前 | 作成時点では連絡先メールが決まっていない |
| `authenticatorSelection.residentKey` | `required` | ユーザー名の入力なしでサインインするため |
| `authenticatorSelection.userVerification` | `preferred` | 対応しない認証器でエラーにせず、サーバーでUVを確かめる |
| `attestation` | `none` | 認証器の機種を制限しないため |
| `pubKeyCredParams` | `-7`（ES256）と`-257`（RS256） | 主要な認証器が対応する組み合わせであるため |
| `excludeCredentials` | そのアカウントの登録済みの資格情報 | 同じ認証器に二重に作らないため |
| `extensions` | `{ credProps: true }` | 発見可能な資格情報として作られたかを確かめるため |

## アカウント作成の流れ

1. 認証前の画面で利用規約への同意を取り、パスキーの作成を押させる。
2. サーバーで`user.id`とチャレンジを作り、ブラウザで`navigator.credentials.create()`を呼ぶ。
3. 検証に通ったら仮登録のアカウントと資格情報を保存し、セッションを発行する。
4. 連絡先メールの入力と確認を求め、確認が済んだら本登録にする。
5. 本登録にしたら`PublicKeyCredential.signalCurrentUserDetails()`で`name`と`displayName`を連絡先メールに更新する。
6. Googleの連携を促す。

確認の時点で連絡先メールが別のアカウントと重複した場合は仮登録のアカウントを消し、`PublicKeyCredential.signalUnknownCredential()`でその資格情報をパスキーの管理画面から消させる。

## サインインの流れ

1. 「パスキーでサインイン」のボタンで、空の`allowCredentials`を渡して`navigator.credentials.get()`を呼ぶ。
2. 資格情報IDでアカウントを引き、見つからなければ`signalUnknownCredential()`を呼んでサインインを失敗させる。
3. 仮登録のアカウントであれば連絡先メールの確認から再開させる。
4. サインインに成功したら`signalAllAcceptedCredentials()`と`signalCurrentUserDetails()`でパスキーの管理画面と情報をそろえる。

サインイン画面にはユーザー名の入力欄を置かないため、入力欄の自動補完に出すConditional UIは使わない。

## サーバーでの検証

- チャレンジは32バイトの乱数とし、セッションに紐付けて保存し、1回使うか5分経ったら無効にする。
- `expectedOrigin`と`expectedRPID`を固定の値で渡し、リクエストの`Origin`ヘッダーから組み立てない。
- 認証器のデータのUVフラグが立っていない応答は拒否する。
- 署名カウンタは保存値と応答がともに0の場合は比べず、0より大きい保存値から増えていない場合は拒否する。
- 同期されるパスキーの多くはカウンタを常に0で返すため、カウンタだけで複製を検出しようとしない。

## 再認証

再認証では、そのアカウントの資格情報IDと`transports`を`allowCredentials`に入れて`navigator.credentials.get()`を呼ぶ。
パスキーがないアカウントはGoogleで再認証させる。

## 管理画面

- パスキーごとに1枚のカードを出し、名前・作成日時・最終利用日時・削除の操作を置く。
- 名前はAAGUIDから提供元（iCloudキーチェーン、Googleパスワードマネージャーなど）が分かればそれを使い、分からなければ作成時のOSとブラウザから付け、利用者が変更できるようにする。
- AAGUIDの名前の対応表として広く使われた`passkey-authenticator-aaguids`は廃止が決まっており、2027年1月6日から空のオブジェクトを返すため、FIDO Metadata Serviceを使い引けない場合も表示が崩れないようにする。
- 削除したら`signalAllAcceptedCredentials()`で残りの資格情報の一覧を伝える。
- `signalAllAcceptedCredentials()`に空の一覧を渡すと利用者のパスキーがすべて隠れるため、空の一覧では呼ばない。

## Signal APIの対応状況

Chrome 132・Edge 132・Safari 26が対応し、Firefoxは対応していない。
呼ぶ前に関数があるかを確かめ、ない場合は何もしない。

## 保存する値

| 値 | 用途 |
|---|---|
| 資格情報ID | サインイン時の検索（一意制約） |
| 公開鍵 | 署名の検証 |
| 署名カウンタ | 複製の検出（タイムスタンプを返す認証器があるため64ビット整数） |
| `transports` | 再認証で`allowCredentials`に渡す |
| AAGUID | 提供元の名前の表示 |
| バックアップ可能（BE）・バックアップ状態（BS） | 同期されるパスキーかどうかの表示 |
| 名前・作成日時・最終利用日時 | 管理画面での表示 |
| `user.id` | アカウントごとに1つ持ち、Signal APIに渡す |

## 複数のドメインとネイティブアプリ

- 別の登録可能なドメインで同じパスキーを使う場合は、`rp.id`のドメインの`/.well-known/webauthn`に`origins`を置く（Related Origin Requests）。
- ネイティブアプリで同じパスキーを使う場合は、AppleではAssociated Domains、AndroidではDigital Asset Linksでドメインとアプリを関連付ける。
