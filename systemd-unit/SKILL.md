# systemd ユニット

個人ホストへ生成するunitの規約と管理スクリプトを持つ。操作の使い方は各スクリプトの`--help`を参照する。

## 使う場面

| 場面 | 操作 |
|---|---|
| アプリの起動口（`just serve`等）をログアウト後も動かす | `user-unit add standing` |
| 定期実行を仕込む | `user-unit add oneshot` |
| 生成済みunitの点検・撤去・再起動 | `user-unit doctor` / `uninstall` / `restart` |

`standing`は常駐プロセス、`oneshot`はtimerが起こすバッチで、serviceとtimerの2本が生成される。CLIが表現できないunitは、生のunitファイルを`user-unit check` / `install`へ渡す。

## 原則

**アプリケーションは通常の起動口だけを提供し、常設の判断はホストが持つ。** `just dev`や`just serve`のような起動口はアプリケーションの責務で、どれをログアウト後も動かすかはホストの判断である。製品として配布するsystemd unitはこの個人ホスト規約の対象外とする。

**`~/.config/systemd/user`の生成済みunitを現在状態の台帳とする。** 失われたホストは、ユーザーの指示と本skillから必要なunitをその都度再生成する。

**unitは一時ディレクトリで具体化してから登録する。** 生成・検証・登録は`user-unit`が行い、登録時に生成元を示すコメントを付けるため、既存unitとの衝突と後日の撤去を追跡できる。

**生成済みunitではホスト固有の絶対パスを許容する。** そのunitは現在のホストだけを表すため、ホーム直下の安定した場所は`%h`を使い、リポジトリの作業ディレクトリは生成時に解決した絶対パスを使う。

## 監視と通知

動作、監視、通知の責務を分ける。

| 層 | 責務 |
|---|---|
| 対象unit | プロセスの起動と再起動 |
| `unit-failure-monitor` | 最初の異常の記録、10分後の状態確認、原因分類、障害イベント生成 |
| `discord-notify` | Discord Embedの表現、配送、配送失敗時の再試行 |

常駐processは`all-stops`、oneshot batchは`failures-only`を配線する。監視・通知unitはホスト全体で1組だけ登録し、テンプレートinstanceの`%i`で対象名を受け取る。

通知されるのは最初の異常から10分後も停止または再起動を繰り返す場合だけである。導入後は復旧した一時障害と継続する障害を別々に実地確認する。

## 秘匿値

正本となるホスト秘密ファイルを1本決め、アクセス権を`600`にする。systemdユニットへは`EnvironmentFile=`で渡す。正本が無い場合は起動せず、設定漏れをその場で露出させる。`user-unit`は値を表示せず書式と権限を検査する。
