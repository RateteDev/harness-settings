# リポジトリ規約・セットアップ

## 目的

リポジトリごとの開発基盤（骨格・コマンド・CI・Gitフック）の仕様差分をなくし、標準化と機械検査によって品質を維持する。

## 進め方

- **新規リポジトリ:** 雛形（`templates/`）を配置して初期設定を行う。
- **既存リポジトリ:** まず監査スクリプトを実行し、現状の差分を確認する。
- **基盤の変更:** `justfile` やCIを修正する際は、下記の規約と雛形に厳格に従う。

---

### 1. 新規リポジトリの立ち上げ

1. `templates/` の内容を対象リポジトリへ配置し、プレースホルダを置換する。

   | ファイル / ディレクトリ | 役割 |
   |---|---|
   | `justfile` | 開発コマンドの統一窓口 |
   | `.github/workflows/ci.yaml` | CIワークフロー定義 |
   | `mise.toml` | ツールチェーンのバージョン宣言（単一の正本） |
   | `.githooks/` | `commit-msg`, `pre-commit`, `pre-push` フック |
   | `.gitignore` | 標準的な除外設定 |

2. 必須のディレクトリ骨格を作成する。

   ```text
   apps/        アプリケーション
   packages/    共有ライブラリ・内部パッケージ
   assets/      静的アセット
   data/        データファイル
   docs/adr/    設計判断の記録（ADR）
   docs/spec/   仕様書
   infra/       インフラ・デプロイ定義
   ```

3. `AGENTS.md` を作成する（雛形はないため、リポジトリの実態に応じて作成）。
4. フックを有効化する。
   ```sh
   git config core.hooksPath .githooks
   ```

### 2. コア規約（機械検査の対象）

- **コミットメッセージ（`commit-msg`）**
  - 件名・本文形式・文字数・「一文一行」を機械検査する。
  - フックが失敗した場合、**メッセージ側を修正し、フック側のルールは緩めない**。
  - このフックは全リポジトリで同一内容を維持する（改修時は雛形を更新して配る）。

- **コミット前検査（`pre-commit`）**
  - 変更パスに応じたアプリ検査に加え、無条件で `repo-checks` を実行する。
  - CIでも同じ `repo-checks` を実行し、リポジトリ全体の不変条件を1箇所で担保する。

- **バージョン管理の単一化（`mise.toml`）**
  - ツールのバージョンは `mise.toml` だけで宣言する。
  - CI（GitHub Actions）では `jdx/mise-action` を使い、ワークフロー内の `env` や `with:` にバージョン番号・リテラル（`*_VERSION` 等）を直接書かない。
    `latest` や `stable` の使用も禁止。

- **`justfile` のドキュメント（`[doc]`）**
  - `just --list` は直前のコメントの最終行だけを説明として表示するため、説明が1行のコメントに収まらないときは `[doc]` 属性で1行の説明を明示する。
  - 複数行のコメントは、背景や理由の記録として残す。

### 3. 設計・実装規約

#### justfile

- **命名規則:** recipeは `{app}-{action}` 形式とし、`[group]` でアプリごとにまとめる。
- **check / fixペア:** 各アプリに必ず対で配置する。
  - `{app}-check`: ファイルを変更せずにlint・フォーマット・型検査を実行（CI / pre-commit用）。
  - `{app}-fix`: 可能な自動修正をすべて実行。
- **カプセル化:** 公開不要な内部recipeには `[private]` を付与し、名前を `_` で始める。
- **引数:** 複雑な引数は避け、デフォルト値を設定する。
  分岐が多い場合はrecipe自体を分ける。
- **スコープ:** `repo-checks` にはリポジトリ全体に常に課す条件のみを記述し、特定アプリ依存の処理は含めない。
- **並列処理:** ジョブをバックグラウンド並列実行する場合は、各PIDを個別に `wait $PID` する（引数なし `wait` はエラー検知が抜けるため禁止）。

#### CI（GitHub Actions）

- **依存の分離:** ジョブはアプリごとの `{app}-ci` と `repo-checks` に分割し、相互に依存させない。
- **recipeの呼び出し:** ステップ内で直接長大なシェルコマンドを書かず、`just` のrecipeを呼び出す。
- **再現性:** 外部Actionはタグで固定する。
- **キャッシュと実行制御:** キャッシュキーにはロックファイルのハッシュを用い、`concurrency` でブランチ内の古い実行をキャンセルする。
- **Workers Builds:** Cloudflare Workers Buildsでjustを導入する場合は、`install.sh --tag <version>` でバージョンを固定する。

### 4. 既存リポジトリの監査手順

1. 以下のコマンドを実行する（`SKILL_ROOT` は本スキルの配置パス）。
   ```sh
   "${SKILL_ROOT}/scripts/audit.sh" --repo <対象リポジトリのパス>
   ```
2. スクリプトは機械検査結果とエージェント向けガイドを出力する。
   終了ステータスに関わらず、ガイドの全項目を確認する。
3. 機械検査とガイドの確認結果を統合してユーザーへ報告する。
4. **検出された問題は独断で修正せず、修正案を提示してユーザーの承認（GO）を得てから対応する。**
