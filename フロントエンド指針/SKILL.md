# 基本姿勢

- UIはユーザーが自分の環境（ズーム、フォントサイズ、入力デバイス、画面サイズ）に合わせて閲覧・操作できるものとして設計する。
- ブラウザ標準の挙動とアクセシビリティを内部的に保持した上で、見た目と体験を整える。
- 装飾は操作・理解を助ける場合にのみ使う。状態変化、階層、操作可能性、現在位置の表現は積極的に使ってよいが、意味のない装飾・過剰なアニメーション・不要なカード化は避ける。
- callout・blockquote・アラート等の左端アクセントラインは直線で切る。`border-radius` で丸めない。

## ヘッダー内の補助機能

ヘッダーは構造・現在位置・主要操作の領域。補助的な設定（フォントサイズ、テーマ、表示密度）を常時テキストボタンとして並べない。

- 補助機能は意味の分かるアイコンに畳み、クリック/タップでポップオーバーやパネルとして展開する。
  - フォントサイズ → `Aa`アイコン → クリックで小/標準/大を選択
  - カラーテーマ → パレットアイコンで現在のテーマ色を示し、クリックで選択肢を表示
  - 表示密度 → 関連設定をまとめた小パネル
- アニメーションは状態変化の理解のためだけに使い、軽いフェード・スライド程度に留める。

## モバイルでの操作設計

デスクトップでヘッダーやサイドバーに配置する主要操作は、モバイルではFAB（Floating Action Button）に移す。

- FABには画面の主目的に応じた主要アクションを割り当てる。何を置くかは画面ごとに決める。
  - 記事ページ → 目次を開いてセクションへジャンプ
  - フィード/一覧 → 新規投稿・新規作成
  - 検索画面 → 検索を開く
- アクションが1つなら単一FAB、複数なら展開型（Speed Dial）を使い分ける。
- 補助的な設定（テーマ、フォントサイズ等）はFABではなくハンバーガーメニューや設定パネルに分離する。FABは画面の主要操作専用。
- FABがコンテンツやスクロール末尾の重要な要素を恒常的に隠さないよう配置に注意する。

## モバイルでの余白累積の抑制

セマンティックHTMLでは body > main > article のようにネストが深くなるが、各要素が独立して padding/margin を持つと余白が累積し、モバイルではコンテンツ領域が極端に狭くなる。

- メディアクエリで横幅が狭い場合、コンテンツの主コンテナ（article等）を画面幅いっぱいに密着させ、外側の要素の余白を無効化する。
- 密着させたコンテナ自身が唯一の `padding-inline` を持ち、画面端とコンテンツの間の余白を一元管理する。
- 外側のセマンティック要素（body, main）や内側のコンテンツ要素はページ余白を持たない。コンポーネント内部の余白（要素間の間隔等）は各コンポーネントが持ってよい。

## カラーテーマ

配色の選択権をユーザーに持たせる。アプリ側で1つの配色に固定しない。

- カラーテーマとダーク/ライトモードは排他で実装する。両方を同時に提供しない。カラーテーマを採用する場合、各テーマが自身の明暗を含む。
- テーマはCSS変数で定義し、切り替え時にルート要素の属性を変更するだけで全体に反映させる。
- 利用可能なパレットは `references/color-palettes.md` に定義する。テーマ名とCSS変数値のセットで管理する。
- コントラスト比はテーマごとに担保する。本文・ラベル・操作部品の文字はWCAG 2.1 AA（通常サイズ4.5:1、18.66px以上の太字または24px以上は3:1）を下限とし、下回る値を採る場合は所有者に確認する。装飾のみを担う罫線・塗りはこの限りではない。

## アイコンの規格

アイコンは操作部品であり、同一アプリ内でライブラリを統一する。以下を全アイコンボタンで揃える：

- 視覚サイズ、線幅/塗りスタイル、ボタン全体サイズ
- クリック/タップ当たり判定（アイコンが小さくても操作領域は十分に確保）
- ボーダー有無・太さ、角丸、内側余白、アイコン間隔
- hover / active / selected / disabled の状態表現、フォーカスリング

アイコンのみで意味を伝える場合は `aria-label`、ツールチップ、状態の視覚表現を付与する。

## 一覧の表示形式

同種のアイテムを一覧する画面では、表示形式（リスト/カード、カラム数）の選択権をユーザーに持たせる。

- 適用対象は「同種アイテムの一覧で、見渡し方に複数の妥当な選択肢がある画面」に限る（画像ギャラリー、記事一覧、ファイル一覧など）。単一コンテンツ閲覧、フォーム、チャット、ダッシュボードには不要。
- 切り替えUIは一覧の直近（一覧上部のツールバー等）に置く。ヘッダーの補助機能とは分離する。ヘッダーはアプリ全体に効く設定、表示形式はその一覧にだけ効く操作。
- 表示形式に応じて情報量とアクションを連動させる。面積が許す量を超えて詰め込まず、面積がある形式では省略しすぎない。
  - リスト（1行1アイテム）: タイトル・日付・ステータス程度。アクションは行末にアイコン1-2個またはコンテキストメニュー。
  - カード1カラム: サムネイル大・説明文・タグ・メタ情報。ボタン複数を露出できる。
  - カード2-3カラム: サムネイル中・タイトル・最小限のメタ。アクションはアイコンのみ、またはホバー/タップで表示。

## 画像アップロードUI

アップロードは「画像を受け入れる大きな領域」として設計する。小さなボタンを主役にしない。

- 領域は以下を同じ操作対象として受け入れる：クリックでファイル選択、ドラッグ＆ドロップ、クリップボード貼り付け
- 内部的にはブラウザ標準の file input・キーボード操作・スクリーンリーダー対応を保持する。
- 状態を明確に示す：未選択、ドラッグ中、読み込み中、アップロード済み、エラー。色・ボーダー・テキスト・アイコン・軽いアニメーションで区別する。
- エラー時は原因と次のアクションを短く伝える。「失敗」だけで終わらせない。

## サイズ単位とズーム設計

単位は役割で使い分ける。レイアウト（画面に対する面の取り方）とコンテンツ（文字・余白の読みやすさ）を分離する。

| 用途 | 単位 |
|------|------|
| レイアウト骨格・コンテナ幅・面の比率 | `vw`, `%` |
| 文字サイズ・本文余白・コンポーネント内部間隔 | `rem` |
| ボーダー・アイコンサイズ・ヘアライン・固定最小寸法 | `px` |
| 本文幅・入力欄・コード表示 | `ch` |

- `vw` を万能として扱わない。極端な画面幅では min/max/clamp を併用する。
- 本文やメイン領域に固定px幅を設定して中央寄せだけの設計は避ける（ズームアウト時に余白が肥大化して浮島になる）。

## 見出し階層

見出しは情報構造をユーザーと支援技術に伝えるために使う。見た目を大きくしたいだけで使わない。

- `h1`：ページ全体の主題のみ。コンポーネント内部やカード内で使わない。
- `h2`：セクション主見出し。`h3`：小見出し。`h4`：さらに細かな区分が必要な場合のみ。
- **`h5`以降は禁止。** ユーザー入力・生成AI出力でも許可しない。入力された場合は変換/保存/生成のいずれかの段階で弾くか、制約をユーザーに短く説明する（黙って変換しない）。
- `h4`を超える階層化が必要なら、見出しを深くするのではなく情報設計を見直す：ページ分割、タブ分割、カード化、リスト化、ラベル、強調表現。

## フォント選択

フォントはテーマ・コンテンツに合ったものを選択する。サイト全体の印象を左右する大きな要素であり、デフォルト任せにしない。

選択時には、使用するフォントで言語・字形起因の問題が起きないかを確認する。

- **数字の字形**: Georgia のようなオールドスタイル数字（テキスト数字）のフォントは、数字ごとに上下へ突き出すため、表・価格・タイムスタンプなど数字主体のUIで行が凸凹に見える。数字を多用する箇所ではライニング数字のフォントを選ぶか、`font-variant-numeric: lining-nums` で揃うことを確認する。
- **和欧混植のフォールバック**: 日本語グリフを持たない欧文フォントを指定すると、日本語部分がフォールバックフォントで描画され、書体の混在やベースラインのずれが生じる。`font-family` のフォールバック指定まで含めて、実際の混植テキストで表示を確認する。

## カードUIの高さ揃え

カードを並べる一覧では、内容の多寡によってボタンやタグの位置がカードごとに上下しないよう、構成要素ごとに領域を固定で確保する。

例えば「画像・タグ・ボタン」構成のカードでは:

- タグ領域はタグが2行入る高さを固定で確保する
- ボタン行は1行分を固定で確保し、常にカード下端に揃える

タグが1行しかないカードでボタンが上に詰まると、隣のカードと高さが一致せず不格好に見える。`min-height` の指定、またはカード内をグリッドにして行の高さを定義することで、内容量に依存しない揃えを実現する。

## サイト内の運用情報導線

サイト内には以下の導線を作成することを基本とする。フッターや専用ページなど、ユーザーが探しやすい定位置に置く。

- 連絡先
- 公開している GitHub リポジトリ / ホームページへのリンク
- 不具合の報告先
- アップデート履歴の確認場所

テンプレートから立ち上げたサイトで漏れやすいため、公開前チェックの対象とする。

## 実装前チェック

実装前に以下を確認する（長い説明は不要、設計に反映すればよい）：

1. 画面の主目的は何か
2. ヘッダーに常時出す操作 vs 畳む補助機能の切り分け
3. モバイルでFABに割り当てる主要アクションは何か
4. カラーテーマの選択肢は用意されているか
5. アイコン操作部品の規格統一
6. 一覧画面がある場合、表示形式の選択権とその連動（情報量・アクション）
7. 画像アップロードがある場合、受け皿として設計されているか
8. レイアウトとコンテンツのサイズ責務分離
9. 見出し階層が h4 以内か。超える場合ページ/タブ分割を検討したか
10. フォントが数字の字形・和欧混植で破綻しないか
11. 公開するサイトなら運用情報の導線があるか

## 優先順位

迷ったときの判断序列：

1. ユーザーが読みやすく操作しやすいこと
2. ブラウザ標準の挙動とアクセシビリティを壊さないこと
3. 情報構造が浅く把握しやすいこと
4. 操作部品の規格が揃っていること
5. ズーム・基本フォントサイズ変更に耐えること
6. 見た目が整っていること
7. 装飾的な個性があること
