# リポジトリ監査

静的チェックツールでは検知できない、リポジトリの構成・規約・運用の妥当性をエージェントが確認する。

## 基本ルール

- `scripts/audit.sh` の実行結果（成否）にかかわらず、以下の全項目を実施する。
- **推測で判断しない**: 必ず対象ファイルを閲覧・確認して判断する。
- **無断修正の禁止**: 指摘事項の修正は行わず、報告のみとする。

---

## 監査チェックリスト

### 1. リポジトリ構成・ドキュメント
- ディレクトリ構成とドキュメント（README等）が、現在のアプリ・共通パッケージ・インフラの実態を反映しているか。
- 未使用の設定ファイル、空の雛形、存在しないパスへの参照が放置されていないか。
- README、CONTRIBUTING、ADR、仕様書、AGENTS.mdの役割が重複していないか。

### 2. AGENTS.md
- 記載内容が現在の構成・運用実態と一致しているか。
- 常時守るべき制約事項のみが書かれているか（一時的な作業手順や、コードから読み取れる冗長な説明が混ざっていないか）。
- サブディレクトリに別の `AGENTS.md` がある場合、責務やスコープが重複していないか。

### 3. justfile
- レシピ名および `just --list` の説明文が、実際の動作と一致しているか。
- `check`（改変なしの検証）と `fix`（自動修正）が対になっているか（`check` がファイルを変更していないか）。
- 内部レシピに `[private]` 属性や `_` 接頭辞が付いているか。
  グループ分けや引数の初期値が適切か。
- 中身が空、`@echo` のみ、または存在しないコマンド・パスを参照するレシピがないか。
- `repo-checks` 等のレシピが、リポジトリ固有の横断的ルールを正しく検査しているか。

### 4. Git hooks
- pre-commitの対象パス条件が、実在するディレクトリと合致しているか。
- commit-msgの検証ルールが、現在のコミット規約と一致しているか。
- justfileやCIと同じ検査ロジックを二重に実装していないか。

### 5. ローカル検証とCI
- CIジョブが独立して実行できる単位に分割されているか。
- ローカルとリモート（CI）で同じ検証レシピが使われているか。
- ロックファイルのハッシュをキーにしたキャッシュ機構が機能しているか。
- ローカル用検証（`ci-local` 等）とリモートCIの検査内容に乖離がないか。
- タイムアウト値や同時実行数（concurrency）がジョブ内容に対して妥当か。

### 6. ツールチェーン
- `mise.toml` 等で指定されたツールと、実際に利用しているツールに過不足がないか。
- バージョン指定が複数の設定ファイルに重複・分散していないか。
- 異なるパッケージマネージャー（npm/pnpm/yarn等）のロックファイルや設定が混在していないか。

### 7. 規約の実効性
- 配置されている設定ファイルやスクリプトが、実際の開発フローやCIから確実に呼び出されているか。
- 検証を回避する抜け道や、廃止済みツール・旧運用への参照が残っていないか。
- 検査の除外設定（ignore）に、妥当な理由があるか。

## 報告形式

機械検査（`FAIL` / `WARN`）とエージェント検査の結果を統合し、**重要度順**に以下の表形式で報告する。  
※問題が一件もない場合も、機械検査・エージェント検査の両方を完了した旨を明記すること。

| 重要度 | 区分（機械 / エージェント） | 対象（ファイル・箇所） | 問題点 | 対処案（要否・根拠） |
| :--- | :--- | :--- | :--- | :--- |
| 高 / 中 / 低 | | | | |
