# AIとシステムの分業設計

## 目的

最終成果物をすべてAIに直接生成させると、次の問題が生じる。
- 座標計算や定型装飾など、機械的に決まる部分にまでトークンを浪費する
- 出力品質が安定せず、修正のたびに大規模な再生成が必要になる
- 参照関係や構文の誤りを機械的に検知しづらい

**解決策：**
AIの出力を「判断と意図を表現する最小限の情報」に絞り、レンダリング・計算・検証はシステム側で行う。
AIの推論リソースを、創造的・文脈的な判断が必要な領域に集中させる。

---

## 基本思想

成果物の生成プロセスを以下のパイプラインとして捉え、境界を明確にする。

```
[人間の意図] → 【AI：意図の解釈・構造化】 → [中間表現] → 【システム：検証・変換・描画】 → [完成品]
```

| 担当 | 役割 | 具体例 |
| :--- | :--- | :--- |
| **AI** | 文脈の理解、取捨選択、構造設計、意味付け | 掲載内容の選定、要素間の関係性定義、強調箇所の判断 |
| **システム** | 形式検証、座標・数値計算、スタイル適用、変換 | スキーマ検証、自動レイアウト、HTML/SVG等のコード生成 |

※分担境界は固定ではない。
全体配置や大枠の構成など、大局的な判断はAIに委ねたほうがよい場合もある。

---

## 設計原則

1. **トークン効率を最大化する**
   - 実装コードや装飾の数値を毎回出力させず、意図・関係性・設定値だけを生成させる。
   - ※短さだけでなく、スキーマ指示の複雑さや修正コストも含めたトータルコストで判断する。
2. **品質を決定論的に担保する**
   - レイアウト計算、カラーパレット適用、構文変換はシステム側に任せ、AIの出力揺らぎによる品質低下を防ぐ。
3. **内容と表現を分離する（保守性・再利用性）**
   - 意味的なデータと描画機構を分離し、同じ出力から別テーマや別フォーマットを再生成できるようにする。
   - 修正時は、完成品全体ではなく該当データのみを部分編集できるようにする。
4. **機械的に検証し、即座にフィードバックする**
   - 出力データ（JSON、Markdown等）の構文・必須項目・参照関係をシステムで自動検証する。
   - エラー時は推測で補正せず、エラー箇所と原因をAIにフィードバックして自律修正させる。

---

## 設計手順

1. **AIの責務を切り分ける**
   - 同じ定型構造や装飾を毎回出力していないか確認する。
   - 機械的な処理（計算・整形・描画）をシステムに切り離し、AIの出力を「成果物を決定づける本質的情報」だけに絞る。
2. **中間表現（フォーマット）を選定する**
   - 最初から独自DSLを作らない。
     既存のMarkdown、JSON、YAML、制約付きHTMLで十分ならそれを採用する。
   - 独自DSLは「既存形式では冗長すぎる」「構文検証を厳格にしたい」などの明確な理由がある場合のみ導入する。
3. **変換・検証機構を実装する**
   - スキーマバリデーション（機械的検証）を用意する。
   - 中間表現を完成品に変換する決定論的エンジン（パーサー・レンダラー）を構築する。
   - ※将来の拡張性を理由に、不要な汎用ライブラリ化や過剰な抽象化をしない。
4. **実運用で費用対効果を評価する**
   - 「直接生成」と「分業生成」を比較し、消費トークン・修正の手間・保守コストを評価する。
   - 構造化自体を目的にしない。

---

## 実例

- **図（ダイアグラム）の生成**
  - **AI:** ノード、リレーション、グループ分け、配置の意図（DSLやJSON）を出力。
  - **システム:** 文字幅の計測、座標計算、配線ルーティング、テーマ・配色の適用を行う。
- **ドキュメントの構造化**
  - **AI:** 厳格なMarkdown＋メタデータ（frontmatter等）で構造と本文を出力。
  - **システム:** 構文検証後、Web表示用HTMLやPDFなどの各媒体形式へ変換する。
- **固定テンプレートへの流し込み**
  - **AI:** スライドや雑誌の「ページ構成」「見出し」「本文」「配置するパーツの種類」を指定。
  - **システム:** ページ送り、レスポンシブ配置、タイポグラフィの適用を担当する。

---

## 限界と注意点

- **直接生成が適している場合もある**
  - 単発のタスク、頻繁に仕様が変わる試作、中間表現に落とし込みにくい自由な表現では、最初からAIに完成形を出力させたほうが速く低コスト。
- **形式的正しさと内容の質は別**
  - 機械的検証が通っても、内容自体の価値（事実関係や論理の妥当性）は保証されない。
    検証の目的を取り違えないこと。

## チェックリスト

設計時に以下を確認する：

- [ ] AIが「毎回同じような定型コードや数値」を出力していないか？
- [ ] AIに渡す指示（プロンプトやDSLの文法）が複雑化しすぎて、トークン削減効果を相殺していないか？
- [ ] システム側の変換エンジンやDSLの保守コストに見合う価値があるか？
- [ ] エラー発生時に、システムがAIに対して修正可能なエラーメッセージを返せているか？
- [ ] 内容（データ）と表現（レンダリング）が明確に切り離されているか？
