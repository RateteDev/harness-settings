# テスト規約

## このスキルの目的

テストを増やすほど実行時間と保守のコストが膨らむ一方、エージェントの変更は局所に閉じ、横断的な故障は起きにくい。
利用者体験を壊す故障の検出を保ちながら、常設テストの総コストを下げる。

## 進め方

テストの採否、置き場、書き方、実行の順に定める。
テストランナーの選定はプロジェクトの裁量とし、本規約はランナー非依存の原則のみを定める。

### テストの採否

常設テストは、壊れると利用者体験が崩壊するユニットの故障だけを対象にする。
エージェントは追加・維持の前に、削除したときに見逃す故障を挙げ、その故障が利用者体験を崩壊させるかで採否を決める。
故障が他の自動検査や変更時の実画面確認で見つかるなら、その確認へ委ねる。
件数やカバレッジは目標にしない。

テストは、確かめることを一文で言い表せる粒度にする。
期待値は仕様から決め、現状の値・設計・設定値や本体と同じ判定関数から取らない。
保存値や内部構造をなぞるテストは、変更のたびに追随が要るだけで、仕様違反を捕まえない。

テストは本体を実際に動かし、実際の入力と出力で確かめる。
テスト内に本体の処理を複製すると、確かめているのはテスト側の処理になる。
HTMLの入れ子全体ではなく、利用者に影響する部分を固定する。

UIを変更したら実画面を開いて見た目を確かめ、配置・折り返し・色・余白を測る常設のブラウザテストは、この確認との重複を踏まえて採否を決める。

次の確認は削減対象とする。

- テスト用の差し替えの自己検証
- 型やライブラリが保証する内容の再確認
- 同じ結果の反復
- 過剰なケース分け

### ディレクトリ構造

テストは各パッケージの `tests/unit/` 配下に置き、`src/` の構造をミラーする。
テストの所在が機械的に定まり、対応する実装が消えた孤児テストを検出できる。
テスト専用のヘルパーは `tests/utils/` へ置く。

```
apps/{app}/tests/
├── unit/
└── utils/
```

### テストの書き方

テストコードでのモック使用を禁止する。
テストは本番と同じ経路のまま、自作モジュールとライブラリの実物を呼び出す。
モックはテストに実装と別の世界を見せ、テストが緑でも本番で壊れる乖離と、モック自体の管理責任を生むためである。

### 実行

テストはjustレシピを通して実行し、自動検査を単一のエントリポイント（例: `just ci-local`）からすべて実行できるようにする。
自動検査には、テストのほかlint・型検査・入力の検査・生成物の一致確認・ビルドを含む。
CIの所要時間は、テストの削除・統合や重複した処理の整理で短縮する。
