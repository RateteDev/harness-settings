# OSS公開

## このスキルの目的

公開は取り消しにくく、秘密情報・権利・再現性の問題は公開後には直しにくい。
公開前に確かめるべきことを確かめ、見本に沿ったREADMEとリリースを備えた状態でリポジトリを公開する。

## あるべき状態

### 秘密情報・端末情報

- 現行ファイルとGit履歴（削除済みファイルを含む）に、秘密情報・個人情報・端末固有情報が無い。
  履歴を作り直して公開する場合は、履歴の確認を省いてよい。
- 機械的に確かめられる範囲は、`scripts/audit.sh <repo>`で検査されている。
- 秘密情報を検出したときの報告には、場所と種類だけがあり、値そのものは含まれていない。

### 権利関係

- 公開対象のコード・素材・依存物を公開・再配布できることを、ユーザーが確認している。

### 再現性

- クリーンなPodmanコンテナで、READMEの導入から実行までを全行程省略せずに通している。
- 公開前の`github:`参照の導入は認証が要るため、ローカルのリポジトリ指定に代えて確かめている。
- 対話認証・実アカウント・実機が要る手順は、エージェントが実行できないため、整理した手順に沿ってユーザーが実行し確認している。

### README・リリースノート

- 本文は日本語で書かれている。
  ユーザーが別の言語を指定した場合だけ、その言語で書く。
- READMEは[README](references/readme.md)の規則を満たしている。
  READMEを書く・直すときに読む。
- 版・タグ・GitHub Releaseとリリースノートは[リリース](references/release.md)の規則を満たしている。
  リリースするときに読む。
- READMEとリリースノートは[見本](references/output-example.md)と並べて点検されている。
  見本に届かない観点は直されており、写せない観点は理由を添えて残課題としてユーザーへ伝えている。

### 公開

- public化の時点で、公開前チェック（秘密情報・端末情報、権利関係、再現性）とREADMEの確認が済み、ライセンスとバッジの文言をユーザーが承認している。
- 履歴から秘密情報・端末情報を除いて公開した場合、リポジトリは削除して同じ名前で作り直され、`main`だけがpushされている。
  force-pushではGitHub側の古いオブジェクトがSHA直指定で到達できる期間が残るためである。
- 公開後の履歴は書き換えられていない。
  書き換えると他者のcloneが壊れるためである。
- 公開後、可視性・既定ブランチ・issues・wikiの設定が意図どおりである。
- 公開後、認証なしの環境から`github:`参照のまま導入できることを1回確かめている。
  公開前にローカル指定で代えた差分を、ここで埋めるためである。

## 守る順序

1. 本スキルに定義の無い作業をユーザーが求めた場合は、作業に入る前に本スキルへ規則を追加する。
   Pagesは公開するコンテンツがまだ無いため定義しておらず、Pagesの公開を求められた場合は`references/pages.md`として段階を定義する。
2. 公開前チェックとREADMEを終え、未解消の項目をすべて解消する。
   public化した後では、漏れた秘密情報や権利の問題を取り消せないためである。
3. ライセンスとバッジの文言について、ユーザーの承認を得る。
4. 履歴を作り直す場合は、削除で失われるもの（star・fork・issue・release・設定）をユーザーへ示し、続行するかと控えを取るかをユーザーが決めてから削除する。
   削除は元に戻せないためである。
5. public化し、公開後の確認を行う。
6. 公開後は、変更のまとまりごとにリリースする。

## 手段

- public化は次のコマンドで行う。

  ```sh
  gh repo edit <owner>/<repo> --visibility public --accept-visibility-change-consequences
  ```

- `scripts/audit.sh <repo>`は、現行ファイル・全履歴・コミット作者を検査し、検出の種類と場所だけを出力する。
  検出があると終了コード1で終わる。
