# Architecture Decision Record

プロジェクトの重要な設計判断を ADR（Architecture Decision Record）として記録する。

## 目的

「なぜそう決めたか」を恒久的に残し、「何を選んだか」だけでなく「なぜそれを選んだか」を後から追跡できるようにする。採用した判断だけでなく、検討の末に見送った判断も記録する。

分岐があり、採らなかった選択肢を挙げられることが ADR の成立条件である。ほかに採りようのない修正や、判断を伴わない調査結果には ADR を作らない。判断材料となる調査・検証の結果は、その判断を裏付ける `根拠` として本文に載せるものであり、それ単体で ADR を起こさない。分岐がなかったもの（仕様上ほかに採りようのない修正、既にそうなっていたと判明しただけの調査）は、何も選んでいない以上 ADR ではない。実装が変わったことは ADR を書く理由にならず、逆に何も変えなかった判断は ADR になり得る。

## 運用

- ADR は `docs/adr/` 配下に 1 判断 1 ファイルで置く。
- 例外として、単一のスキルやパッケージの内部でのみ効く設計判断は、その配布物に同梱する参照文書に置いてよい。判断が効く場所と、その判断を読む場所を一致させるためである。`docs/adr/` へ隔離すると、配布物だけを読む利用者から見えなくなる。
- 同梱する場合も、置き場以外の規約は変わらない。ファイル名・フォーマット・書き換えない原則は本規約に従い、配布物の中に ADR 用のディレクトリを設ける。本規約より前に書かれた文書は、形式を揃えるための書き換え対象にしない。
- ファイル名は `YYYYMMDD-hhmm-{h1のタイトル}.md` とする。日時は判断を記録した日時を表し、ディレクトリ内の時系列ソートと同日複数 ADR の順序付けを担う。
- タイトル部分は h1 と完全一致させる。一致を機械的に保てるよう、h1 にはバッククォート・空白・`/` を含めない。
- 一度書いた ADR は書き換えない。判断が覆った場合は新しい ADR を追加して積み重ねる。状態管理のメタデータは持たず、日時の新しい ADR が古い ADR に優先する。
- 記述が現状と食い違っていても、それは書き換える理由にならない。ADR は決定時点の記録であり、当時の事実誤認も、その後の変更で古くなった記述もそのまま残す。直すのはコードか、新しい ADR のほうである。誤字のように判断の内容へ触れない訂正だけを例外とする。
- 過去の ADR に触れる場合は、Markdown リンク `[短い呼び名](ファイル名.md)` で参照し、背景の書き出しで経緯を接続する。表示には文脈に合う短い呼び名、参照先には正式なファイル名を使う。

## フォーマット

文書は h1 のタイトル 1 つで始める。h2 は `背景`・`判断`・`根拠` の 3 つに固定し、この順で書く。h2 は増やさず、内容の多様性は各セクション配下の h3 で表現する。

本文に日付や状態を書かない。日時はファイル名とコミットが、判断の新旧は ADR の積み重ねが担う。

- `背景` — 何が問題で、どの制約や経緯から検討に至ったか。
- `判断` — 何を採用・見送り・保留したか。結論を 1〜2 文で先に述べる。確定していない場合も、何を決めて何を決めていないかを明示する。
- `根拠` — 判断を裏付ける理由・検証・調査の詳細。

h3 の例:

- `判断` 配下: `影響`（判断そのものの条件ではなく、判断の外側へ波及する変化）、`未決事項`（本 ADR で扱わず後続の判断に残した論点）
- `根拠` 配下: `理由`（箇条書き）、`検証結果`（実験・計測）、`調査結果`（外部仕様・代替案の比較）

`理由` には判断の決め手だけを書く。背景で述べた問題の再説明や、検証結果・調査結果に載せる数値の再掲は含めない。

テンプレート:

````markdown
# {判断のタイトル}

## 背景

{問題・制約・ここに至る経緯}

## 判断

{採用・見送り・保留の結論を 1〜2 文で}

### 影響

{該当する場合のみ}

## 根拠

### 理由

- {箇条書き}

### 検証結果

{該当する場合のみ}
````

## 書き方

- 常体（〜である・〜とした）で書く。テンプレートの穴埋めではなく、経緯がそのまま読める文章にする。
- 背景は 2〜4 文で「問題 → 試した経緯 → なぜこの検討に至ったか」を圧縮する。
- 計測値・バージョン・HTTP ステータス・外部ライブラリ名など、判断の材料になった数字と固有名には具体値を書く。「問題があった」のような抽象表現だけで済ませない。
- 内部実装の関数名・定数名は、リファクタリングで陳腐化して読解の負荷にもなるため、判断の言葉に言い換える。識別子そのものが判断の対象である場合に限り記載する。
    - NG: `publishDueScheduledPosts` が `urlPreviews` を空で渡すため kick が走らない
    - OK: 公開の瞬間にプレビューを取得するクライアントが存在せず、検索索引の作成が始まらない
- ファイル名・関数名・コマンド名・ライブラリ名などのコード識別子は、必ずインラインコードにする。ただし h1 はファイル名と一致させるため例外とし、識別子も装飾なしで書く。
- 地の文は短文を並べず、接続して経緯を示す。ただし 1 文は 100 字を目安とし、超えるなら文を分ける。
- 箇条書きは 1 項目 80 字以内・読点 2 つまでを目安とし、体言止めを許容する。収まらない内容は箇条書きをやめ、強調を見出し代わりに置いた文章か h3 へ格上げする。
- 同じ事実を繰り返さない。背景で述べた失敗や制約を根拠で再度扱う場合は、表への整理など別の形に寄せる。
- 「〜する予定である」といった将来の約束は書かない。未決の論点は `判断` 配下の `未決事項` に書く。

## 図表の使い分け

- 比較・一覧は表に、注意・制約・リスクは明示的な注記に、構造は mermaid に寄せる。
- どの h2・h3 でも「一目で概要をつかめるか」を基準に組み立てる。関係・流れ・収束といった構造を持つ内容は文章より先に mermaid で示し、文章は図の補足に回す。
- よく使う型:
    - **収束図** — 複数の理由・条件が 1 つの判断へ集約する `flowchart`。
    - **処理フロー** — 現状構成や手順を示す `flowchart TD`。問題の焦点となるノードだけを警告色にする。
    - **シーケンス図** — クライアント・サーバー・外部サービスなど、登場者間のやり取りを `sequenceDiagram` で示す。
- 図の数に上限は設けず、1 つの構造につき 1 図とする。構造のない内容を図にせず、同じ構造の図を焼き直して並べない。同じ内容を図と文章で二重に述べない。
- `flowchart` は `classDef` でノード種別を色分けし、フェンス内 frontmatter の `title:` でラベルを付ける。
- ダイアグラムは `flowchart`・`sequenceDiagram`・`erDiagram`・`stateDiagram`・`pie` に限定し、ノードラベルに HTML タグを入れない。

## Markdown 互換性

ADR は Markdown レンダラーでそのまま表示できる形式を保つ。ファイル冒頭に frontmatter を書かず、h1 から始める。

## チェック

初稿を書き終えたら、`references/checklist.md` を記述者とは別のエージェントへ渡して判定させ、指摘を修正してから提出する。
