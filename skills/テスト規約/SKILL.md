# テスト規約

## 目的

無駄なテストの作成・保守コストを抑え、CI時間を短縮する。
「テストの量」ではなく、「ユーザー体験を損なう重大な不具合を防げているか」を重視する。

## 1. テストの採否基準

**「壊れたときにユーザー体験が崩壊するか？」** を唯一の採用基準とする。
テストの件数やカバレッジを目標にしてはならない。

### テストを作成・維持する条件
- 削除した場合、ユーザー体験を損なう致命的な不具合を見逃すリスクがあること。

### テストを作成しない（または削除する）条件
- 型定義や外部ライブラリがすでに動作を保証している
- lintやビルド、手動での画面確認で検知できる
- UIの見た目（配置・余白・色など）の微小な差異の検証
- 単なる実装コードのなぞりや、過剰な境界値・ケース分け
- テスト内でのみ使われる差し替え処理（スタブ等）の検証

## 2. テストの書き方

- **モック（差し替え）は原則禁止**
  - 自作モジュールやライブラリは実物を呼び出す。
  - モックを使うと「テストは通るが本番で壊れる」乖離と、モック自体の保守コストが生じるため。
- **1テスト＝1つの検証**
  - 検証内容が1文で説明できる粒度にする。
- **期待値は「仕様」から決める**
  - 現在の実装値や内部構造をそのまま期待値にしない（実装変更のたびにテスト修正が必要になるため）。
  - 実装と同じ判定関数をテスト内で再実装・流用しない。
- **入出力で検証する**
  - 内部状態ではなく、実際の入力に対する出力を検証する。
  - HTML等の出力検証は、全体一致ではなくユーザーに影響する最小限の要素のみを対象とする。

## 3. ディレクトリ構造

テストは `tests/unit/` 配下に置き、`src/` の構造をそのままミラー配置する（不要になった実装の孤児テストを検出しやすくするため）。
テスト用のヘルパー関数は `tests/utils/` に置く。

```text
apps/{app}/tests/
├── unit/   # src/ と同じ構造で配置
└── utils/  # テスト共通ヘルパー
```

## 4. テストの実行

- 自動検査（lint、型検査、テスト、ビルド）は `just` コマンド（例: `just ci-local`）で一括実行できるようにする。
- CI実行時間を短縮したい場合は、設定の小細工ではなく、**不要なテストの削除・統合**で対応する。
