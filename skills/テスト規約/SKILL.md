# テスト規約

## このスキルの目的

テストを増やすほど実行時間と保守のコストが膨らむ一方、エージェントの変更は局所に閉じ、横断的な故障は起きにくい。
利用者体験を壊す故障の検出を保ちながら、常設テストの総コストを下げる。

## あるべき状態

### テストの採否

- 常設テストは、壊れると利用者体験が崩壊するユニットの故障だけを対象にしている。
- 各テストについて、削除したときに見逃す故障を挙げられ、その故障は利用者体験を崩壊させる。
- 他の自動検査や変更時の実画面確認で見つかる故障は、その確認に委ねられている。
- テストの量は、件数やカバレッジではなく上の判定だけで決まっている。
- UIを変更したときは実画面を開いて見た目を確かめてある。
  配置・折り返し・色・余白を測る常設のブラウザテストは、この確認との重複を踏まえて採否が決まっている。
- 次の確認は常設テストから外れている。
  - テスト用の差し替えの自己検証
  - 型やライブラリが保証する内容の再確認
  - 同じ結果の反復
  - 過剰なケース分け

### テストの書き方

- 各テストは、確かめることを一文で言い表せる粒度である。
- 期待値は仕様から決まっている。
  現状の値・設計・設定値や本体と同じ判定関数から取った期待値は、変更のたびに追随が要るだけで、仕様違反を捕まえないためである。
- テストは本体を実際に動かし、実際の入力と出力で確かめている。
  テスト内に本体の処理を複製すると、確かめているのはテスト側の処理になるためである。
- HTMLの出力は、入れ子全体ではなく利用者に影響する部分だけを固定している。
- **テストコードにモックは無い**。
  テストは本番と同じ経路のまま、自作モジュールとライブラリの実物を呼び出している。
  モックはテストに実装と別の世界を見せ、テストが緑でも本番で壊れる乖離と、モック自体の管理責任を生むためである。

### ディレクトリ構造

- テストは各パッケージの`tests/unit/`配下にあり、`src/`の構造をミラーしている。
  テストの所在が機械的に定まり、対応する実装が消えた孤児テストを検出できるためである。
- テスト専用のヘルパーは`tests/utils/`にある。

```text
apps/{app}/tests/
├── unit/
└── utils/
```

### 実行

- テストランナーはプロジェクトが選んでおり、この規約の状態はどのランナーでも成り立つ。
- テストはjustレシピを通して実行され、自動検査は単一のエントリポイント（例: `just ci-local`）からすべて実行できる。
  自動検査には、テストのほかlint・型検査・入力の検査・生成物の一致確認・ビルドが含まれる。
- CIの所要時間は、テストの削除・統合と重複した処理の整理で短縮されている。
