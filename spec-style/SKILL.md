# spec-style

仕様書は対象ごとに形が違う。章立て・図・表の形は対象に合わせて決めてよい。このスキルは、どの対象であっても仕様書として成り立たなくなる書き方だけを禁じる。

## 正本が他にあるものを写さない

仕様書は写しを持たない。次のものは仕様書の外に正本がある。

| 書かれがちなもの | 正本 |
| --- | --- |
| ファイル構成、処理の手順、テスト方針 | ソースとソース内コメント |
| 設定ファイルの記述例、セットアップのコマンド例 | 設定ファイルそのもの、`justfile` |
| その形に決まるまでの経緯 | `docs/adr/` |

写しがあると、片方だけが直された状態に必ずなる。仕様書に置くのは、外から観測できる契約と、それが何のためにあるかだけである。

## 実体を読まずに書かない

既存の状態を述べる記述は、実コードと実設定を読んでから書く。憶測で埋めない。

## 揺れのある書き方をしない

読み手が挙動を一意に決められない書き方を禁じる。

- 同じ対象を、箇所ごとに違う語で呼ばない
- 「〜する場合がある」「原則として」で挙動を確定させない
- 数値で決まっている制約（サイズ上限・期限・タイムアウト）を言葉でぼかさない
- 正常系だけを書き、異常系に触れずに終えない

内部の分岐であっても、外から観測できる違いを生むなら書く。観測できない分岐は、書けばソースの写しになる。

## 書かないものについて書かない

「一般的な技術用語は対象外」「アクセス回数は無制限」のように、そこに無いものの説明を本文へ混ぜない。読み手は、書かれている以上その先を探す。

非目標だけは例外とする。スコープの誤読を防ぐ働きがあるため、1箇所へまとめる場合に限り書いてよい。本文へ散らさない。

## 見出しに番号を振らない

章の順序は書きながら変わる。番号があると入れ替えのたびに手戻りが出る。
