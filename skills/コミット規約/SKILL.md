# コミット規約

## このスキルの目的

コミットは、数か月後の読み手が差分だけでは分からない意図を追う手掛かりになる。
通常コミットとマージコミットの件名と本文の書き方を揃え、`commit-msg`フックの機械検査で規約違反を止める。

## あるべき状態

### 件名

- 通常コミットの件名は`[{scope}]{type}: {日本語の概要}`の形である。
  - `{scope}`は対象範囲で、リポジトリ全体は`[repo]`、アプリ単位は`[frontend]`など、共有部分は`[packages]`または`[shared]`である。
  - `{type}`は`feat`・`fix`・`refactor`・`docs`・`chore`のいずれかである。
- ADRファイルを追加する通常コミットは、件名末尾に`#ADR`が付いている。
  `git log --grep='#ADR'`で判断の履歴を追えるようにするためである。
- マージコミットの件名は`{branch} をマージ: {日本語の概要}`の形で、`{branch}`はマージ元のブランチ名である。
  ブランチ名と「をマージ」の間の半角空白は、フックが形式として要求する。
- 概要は「何をしたか」を1文で表し、終止形を基本として体言止めも使う。
  件名は見出しなので句点で閉じない。

### 本文の構成

- 本文は必ずあり、差分に無い情報だけを載せている。
- 通常コミットの本文は、次の見出しをこの順に置いている。
  1. `## 背景`：観測した事実と動機。
  2. `## 方針`：解法・理由・退けた案。
     変更の足し引きの列挙は差分に任せる。
  3. `## 効果・影響`：利用者が観測する体験・振る舞いの変化。
     差分やテスト・CIの備考から読み取れる実装の細部は、変わらない点も含めて差分に任せる。
- マージコミットの本文は、次の見出しをこの順に置き、通常コミットと同じ文体と作成ルールに従っている。
  1. `## サマリー`：マージの目的と到達状態。
  2. `## 含まれる変更`：変更を振る舞いの単位で挙げる。
  3. `## 残課題`：マージ後に残る作業。
- メッセージ全体は600文字以内である。
  超過したときは重要度の低い情報を削って収め、接続詞や助詞は残す。

### 行

- 本文は1文を1行に収め、句点で閉じている。
  句点で閉じないのは、件名・`#`で始まる行・空行・コードフェンス内・`|`で始まる表行だけである。

### 文体

- 数か月後の読み手を対象とし、背景の1文目で変更前の状態を示している。
  対象は指示語やリポジトリ固有の呼び名で済ませず、それ自体の名前で示す。
- 本文は箇条書きでなく散文で、内部仕様の列挙ではなく外部から観測できる変化を中心に書いている。
- 文と文は、因果・順接・対比・逆接を表す接続表現でつながっている。
  背景の問題は「〜ため」「〜ことから」で方針の行動へ結び、理由は「ためである」のような独立文にせず前の文へ畳む。
- 修飾は対象の直前に置いて文に溶かしている。
  補足を文末の括弧や文片として後置した例を×、修飾を対象の直後の括弧に置いた例を△（許容）、文に溶かした例を○（推奨）として示す。

  ```markdown
  × `tags`パラメータを追加した（CSV、最大10件）。
  △ `tags`パラメータ（CSV、最大10件）を追加した。
  ○ `tags`パラメータをCSVで最大10件まで受け付けるようにした。
  ```

  ```markdown
  × `just clean`は生成物だけを削除する。依存関係まで消すと次の検査が遅くなるため。
  ○ 次の検査を遅くしないため、`just clean`は依存関係を残して生成物だけを削除する。
  ```

- `効果・影響`は、実装の数値ではなく利用者から見た変化で書いている。

  ```markdown
  × h2は番号・本文・罫線・ボタンの順に並び、ボタンは画面幅に関わらず右端に揃う。見出しから段落までのすき間は14pxから24pxへ広がった。描画テストの期待値を更新し、CIは通過している。
  ○ リンクボタンが番号と本文の間を挟まなくなり、見出しを読む際の流れが分断されなくなった。見出しと内容の間隔が広がり、節の区切りが読み取りやすくなった。
  ```

- 英単語と日本語の混在は最小限で、識別子・コマンド名・固有名詞だけを原語で書いている。
- 本文は重要な変更に絞り、細部は差分に任せている。
- 言及する別リポジトリは公開リポジトリだけである。
- 通常コミットは次の例と同じ形と文体である。

  ```markdown
  [api]fix: リクエストボディをzodで検証し、不正な入力を400で拒否する

  ## 背景

  これまで`POST /todos`はリクエストボディを型アサーションで信頼して処理しており、`title`の欠落や空文字でもそのまま保存できてしまっていた。
  入力チェックはフロント側にしかなく、APIを直接叩くクライアントからの不正な入力は素通りしていた。

  ## 方針

  不正な入力を拒否するため、リクエストボディをzodのスキーマで検証し、違反時は詳細付きの400を返すようにした。
  バリデーションを各ハンドラに散らすと重複するため、`createTodo`の入口でひとまとめにした。

  ## 効果・影響

  `POST /todos`は`title`の欠落や空文字を400 Bad Requestで拒否し、不正データはDBに到達しなくなった。
  正常なリクエストは従来と同じレスポンスを返すため、フロント側の変更は不要である。
  ```

### 下書き

- 下書きは一時ディレクトリの`commit-draft-{title}.md`に置かれ、コミット後には削除されている。

## 守る順序

1. 背景と方針がユーザーの明言と差分から読める事実だけで書けているかを確かめる。
   意図を推測で補った場合は、コミット前に要点をユーザーへ提示して確認を得る。
   推測した意図が事実として履歴に残ると、後から訂正するには履歴の書き換えが要るためである。
2. 確認が済んだ下書き、または推測を含まない下書きでコミットする。

## 手段

- コミットは`git commit -F <下書きのパス>`で行う。
- `commit-msg`フックは、件名の形・必須見出し・本文の行末の句点・600文字の上限を検証し、違反するとコミットを止めて理由を表示する。
