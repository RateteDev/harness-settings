# 認証フロー設計

## このスキルの目的

公開サービスの認証を、パスキーとGoogleサインインが互いの予備となる最小の構成にそろえる。
パスワードや回復コードをなくし、画面の説明文と遷移を最小限にする。

## あるべき状態

### 認証手段

- 認証手段はパスキーとGoogleサインインの2つに限る。
- メールのOTPやリンク、認証アプリ（TOTP）、パスワード、回復コードは採用しない。
- Sign in with AppleはiOSアプリを出し、App Store審査ガイドライン4.8でGoogleの代わりのログイン手段を求められる場合に限って加える。
- 依頼者の要望がこの方針と競合する場合は設計の前に指摘し、採否の理由を示して合意を取る。

### アカウント

- アカウントは内部の識別子で持ち、Googleアカウントは`sub`、パスキーは資格情報IDで紐付ける。
- アカウントは連絡先メールの確認前を仮登録、確認後を本登録の状態で持つ。
- メールアドレスは連絡と重要な通知だけに使い、サインインと回復には使わない。
- メールアドレスが一致してもアカウントを自動で統合しない。
- すべての認証手段を失うとアカウントを復旧できないことを登録前の画面と設定画面に明記する。

### サインアップ

- 初期画面は主ボタンをGoogleサインインとし、その直下にパスキーの選択肢と利点を1行で置く。
- 利用規約への同意は認証前の画面で取る。
- 属性（生年月日・性別など）の入力やパスワードの設定を求めない。
- 表示名とアイコンはGoogleプロフィールの値を初期値にする。
- 認証後の必須の手順は連絡先メールの確認だけとし、確認が済むまで本登録にしない。
- 本登録の直後にもう一方の手段（Google登録者にはパスキー、パスキー登録者にはGoogle）の追加を促す。
- ログインなしで使えるサービスでは、価値を体験させた後に登録を促す。

### 回復と手段の管理

- 専用の回復フローは作らず、残った手段でサインインして失った手段を登録し直す。
- 手段が1つだけのユーザーには、失うと復旧できないことを警告して予備の登録を促す。
- 手段の追加・削除と連絡先メールの変更の前に、今ある手段で再認証させる。
- 最後の1つの手段は削除させない。
- 手段を追加・削除したら、操作した端末以外の全セッションを無効にし連絡先メールへ通知する。

### 画面

- 画面は見出し・最小限の入力欄・主ボタン1つを基本とし、補足文を置かずラベルとプレースホルダーで意図を伝える。
- メールの入力とコードの入力は同じ画面を状態で切り替えて使い、似た画面を増やさない。
- 見た目は簡素なモノクロ調とし、パスキーの文言とアイコンは[Passkey Central](https://www.passkeycentral.org/design-user-journeys/principles)の指針に従う。
- Googleのボタンは他の手段と同じかそれ以上に目立たせ、Googleのブランドガイドラインに従う。

### 検証と報告

- メールの変更・追加連携の省略・途中離脱など全分岐で、動作とアカウントの状態を確かめる。
- 画面に余計な説明文が混ざっていないかを確かめる。
- 専門用語を避けて平易に報告し、仕様の判断に迷う箇所は独断せず依頼者に確かめる。

## 手段

- Googleサインインを実装・レビューするときは[Googleサインイン](references/Googleサインイン.md)を読む。
- パスキーを実装・レビューするときは[パスキー](references/パスキー.md)を読む。
- 連絡先メールの取得・確認・変更・通知を実装・レビューするときは[連絡先メール](references/連絡先メール.md)を読む。
- 採否の理由を依頼者に示すとき、または採否を見直すときは[認証手段の採否](references/認証手段の採否.md)を読む。
- 運営者にもデータを読ませない暗号化を求められたときは[PRF暗号化](references/PRF暗号化.md)を読む。
- 登録と分岐の画面の動きは[デモ](references/auth-flow-demo.html)で確かめる。
- 主要サービスの登録画面の事例は[Mobbin](https://mobbin.com/)で探す。
