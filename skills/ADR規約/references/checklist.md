# ADRレビュー指示書

対象のADR（アーキテクチャ決定記録）をレビューし、以下の基準に基づいてフィードバックを提供してください。

## 実行ルール

1. 対象ADRを精読し、後述のチェック項目を判定する。
2. 指摘がある場合は、以下のフォーマットで出力する（修正案は提示するが、ファイル自体の直接編集は行わない）。
   - **該当項目**: （チェック項目名）
   - **問題箇所**: （具体的な箇所や引用）
   - **修正方針**: （具体的な直し方や改善案）
3. 設計判断そのものに対する異議・懸念は、指摘とは別に「**作成者への確認事項**」として記載する。
4. 指摘事項が一切ない場合は、「問題は見つかりませんでした。」と1文のみ出力する。

---

## チェック項目

### 1. 構成・ファイル命名
- [ ] **ファイル名**: `YYYYMMDD-hhmm-{h1のタイトル}.md` の形式であり、タイトル部がh1と完全一致している
- [ ] **見出し構造**: 
  - h1は文書内に1つのみ（記号 `、空白、`/` を含まない）
  - h2は `## 背景` と `## 判断` の2つのみ
  - `## 判断` 配下に、個別の判断内容ごとに `### （判断タイトル）` がある
  - 各h3の直下に、本文と `**根拠**` がこの順で置かれている
- [ ] **不要な情報**: frontmatter（YAMLメタデータ）や日付が本文に含まれていない

### 2. 決定内容の妥当性
- [ ] **分岐と非採用案**: 複数の選択肢を比較検討した記録があり、「採用しなかった選択肢」が明記されている
- [ ] **決定事項の確定度**: 確定事項のみを記載し、未決定の論点や未来の予定・確約表現（「〜する予定である」「〜したい」等）が含まれていない
- [ ] **結論の即時性**: 各判断（h3）の結論が、冒頭の1〜2文で明確に述べられている
- [ ] **根拠の独立性**: `根拠` が `背景` の単なる繰り返しになっていない

### 3. 記述の具体性と表現
- [ ] **具体値の記載**: 判断の決め手となった数値や固有名詞が具体的に残されている
- [ ] **抽象度の統一**: 内部実装の識別子（コード上の変数名や関数名など）に依存せず、アーキテクチャ上の言葉に置き換えられている
- [ ] **重複の排除**: 同じ事実や同一の数値が別セクションで無駄に繰り返されていない
- [ ] **図解**: プロセス、依存関係、状態遷移などの構造的な説明にはMermaidが用いられている

### 4. 文章量・可読性
- [ ] **文の長さ**: 地の文は1文100字以内、箇条書きは1項目80字以内（かつ読点は2つまで）に収まっている
- [ ] **文の接続**: 単文の羅列を避け、「対象」とその「理由・方法」が1文の中に過不足なく整理されている
