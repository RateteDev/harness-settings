# AGENTS.md規約

## このスキルの目的

エージェントへの指示が複数の文書へ散ると、どれが正本か分からず、同じ規則が食い違う。
`AGENTS.md`だけを指示書の正本とし、適用範囲の異なる指示をそれぞれの範囲へ置くことで、重複と矛盾のない常時指示を保つ。

## あるべき状態

### 置き場

- 指示書の正本は`AGENTS.md`にし、同じ規則は1か所にだけ書く。
- 適用範囲の異なる指示は、その範囲の`AGENTS.md`に置く。
- この規約はプロジェクトスコープの`AGENTS.md`に適用する。
  グローバル（ユーザー共通）の`AGENTS.md`は、ユーザーと相談して書く。
- マシン固有の運用情報（稼働中のunit・絶対パス・端末・ローカルツール）は、プロジェクト直下の`AGENTS.md.local`に置き、`.gitignore`で除外する。
  ハーネスのフックは、プロジェクト側ではセッションを開始したディレクトリの直下にある`AGENTS.md.local`だけを読み、親ディレクトリへは遡らずにセッションの冒頭へ注入するためである。
- リポジトリの`AGENTS.md`は実運用の情報を`AGENTS.md.local`に任せ、マシン依存の値（絶対パス・端末名・unit名・ホスト名）の代わりに一般名で書く。
- `AGENTS.md.local`の形式は[実例](examples/my-r2.AGENTS.md.local)に揃える。

### 章構成

- `AGENTS.md`は動機から規則へ進む5章で構成し、章名と順序、各章のつながりは[例](examples/my-r2.AGENTS.md)に揃える。
  1. 問題：作る前に困ったこと。
  2. 方針：解決の軸。
  3. 前提：方針を成立させるコード外の条件。
  4. 配備方法：ホスト直接・バイナリ・dockerなど、利用できる配備方法のヒントだけ。
     ヒントが無いリポジトリでは章ごと省く。
  5. 規則：常時守る制約の表。
- 問題・方針・前提は、ソースだけでは確定できないため、所有者へのヒアリングで確かめた内容を書く。
- 規則表に書く事実は、所有者へ尋ねる前にソースと履歴で確かめる。
- 書く事実と制約は、すべて対象リポジトリのものにする。
  例は実際のリポジトリを題材にした完成例で、その製品固有の事実と制約を含むためである。
- 既存の`AGENTS.md`が英語で書かれていた場合は、その内容を信用せず、調査とヒアリングから1から書き直す。

### 規則表

- 制約は「規則 | 理由」の2列の表に書き、すべての行に理由を添える。
  理由が無いと「今回は例外だろう」と判断されるためである。
- 規則は「〜する。」、理由は「〜のため。」と言い切る。
- 表には、次の変更が破ってもコンパイルやテストが止めない「あってはならない形」だけを載せる。
  `ls`や設定ファイルで復元できる構成の写しは、それらに任せる。
- コードやアーキテクチャが強制する不変条件は、規則表ではなく問題か方針に書く。
- 否定形の規則には代替を添える。
- 別文書を読ませる規則には、そのパスと「いつ読むか」を書く。

### 文体

- 日本語の平叙文で書き、比喩や警句の代わりに事実と規則をそのまま述べる。
- 識別子・パス・固有名詞は原語で書く。
