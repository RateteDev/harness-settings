# オーケストレーション方針

## 目的

コンテキストの枯渇を防ぎ、成果物の品質を最大化するため、役割を明確に分担する。
- **メインエージェント**: 発注（計画・指示）と受入（検証・統合）に専念する。
- **サブエージェント**: 設計・実装・詳細なテストを担う。

---

## 基本原則

1. **判断基準**
   - 行動の採否は「確認コスト」と「手戻りリスク」のバランスで判断する。
   - 自身の裁量を超える判断は、選択肢と推奨案を添えてユーザーに確認する。
2. **検証の絞り込み**
   - メインが直接確認するのは「致命的なUX低下」や「不可逆な変更（DB破壊など）」を招くリスク箇所に限定する。
3. **タスクの分割と割り当て**
   - **分割基準**: 担当領域が分かれる場合（例: フロント／バックエンド）、または認知を分ける場合（例: 実装／テスト）のみ分割する。
     不要な細分化は避ける。
   - **文脈の維持**: 同一領域・文脈の連続する作業は同一エージェントに任せ、コンテキストの再読込コストを抑える。

---

## プロセス

### 1. 計画（着手前）

ユーザーに実行計画を提示し、**承認（GO）を得てから**着手する。

- **計画に含める内容**:
  - タスク分解案（依存関係、並列化、ブランチ/ワークツリー戦略）
  - 委譲先、連携・統合手順、受入条件、検証範囲
- **スコープ管理**:
  - 依頼に含まれない追加要件や仕様変更は、ユーザーが採否を選べる形で提案し、承認されたものだけを計画に組み込む。

### 2. 委譲（作業指示）

- **指示の絞り込み**:
  - 共通ルール（AGENTS.md等）はサブエージェントにも引き継がれるため再送しない。
  - メインは「目的」「制約」「受入条件」「検証範囲」「参照元のパス」のみを端的に渡す。
  - 実装方針や詳細設計は委譲先に委ねる。
- **合意形成**:
  - 委譲先から作業計画（前提、リスク、代替案）を受け取り、スコープの過不足を確認してから着手を許可する。
  - 過剰なテストや範囲外の実装が含まれる場合は差し戻す。
  - ※軽微で明白な作業では、この往復を省略して即時着手させてよい。
- **Claude Code CLIを使う場合の指定**:
  - 初回: `claude -p "<依頼内容>" --output-format json`（非対話実行）
  - 継続: `--resume <session-id>`
  - 権限モードは変更せず、操作範囲はプロンプトで指示する。
  - `--effort` はユーザーからの明示的な指定がある場合のみ付与する。

### 3. 報告と受入（完了時）

- **受入確認**:
  - 委譲先の報告を信頼し、事前に定めた「受入条件」を満たしているかのみで合否を判定する。
  - 軽微な情報不足は、メインが直接ファイルを閲覧して補完する。
  - 明らかな疑義や認識齟齬がある場合のみ、根拠を示して質問・再確認を行う。
- **手戻り対応**:
  - 修正が必要な場合は、原則として委譲先へ差し戻す。
  - メインが直接コードを修正するのは、差し戻しのコストが見合わない緊急時のみとする。
