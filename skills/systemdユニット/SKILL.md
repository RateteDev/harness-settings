# systemdユニット

## このスキルの目的

常駐サーバーや定期実行を手作業で起こすと、ホストの再起動や障害で状態が失われ、停止にも気づけない。
unitの生成・監視・通知・秘匿値の扱いを規約化し、ホストの状態を追跡して復元できるようにする。

## あるべき状態

### 責務の置き場

- アプリケーションは`just dev`や`just serve`のような通常の起動口だけを提供し、どれをログアウト後も動かすかはホストが判断している。
- レポにunit定義は無く、配備方法（ホスト直接・バイナリ・docker等）のヒントだけがある。
- unitの実体はホストの`~/.config/systemd/user`にあり、運用状態はプロジェクトの`AGENTS.md.local`にある。
- `~/.config/systemd/user`の生成済みunitが、ホストの現在状態の台帳になっている。
  ホストが失われた場合は、ユーザーの指示と本スキルから必要なunitをその都度再生成する。

### unit

- unitは一時ディレクトリで具体化・検証してから`user-unit`で登録されており、生成元を示すコメントが付いている。
  既存unitとの衝突と後日の撤去を追跡できるためである。
- 生成済みunitには、ホスト固有の絶対パスがあってよい。
  そのunitは現在のホストだけを表すため、ホーム直下の安定した場所は`%h`で、リポジトリの作業ディレクトリは生成時に解決した絶対パスで書かれている。

### 監視と通知

動作・監視・通知の責務は次のように分かれている。

| 層 | 責務 |
|---|---|
| 対象unit | プロセスの起動と再起動 |
| `unit-failure-monitor` | 最初の異常の記録、10分後の状態確認、原因分類、障害イベント生成 |
| `discord-notify` | Discord Embedの表現、配送、配送失敗時の再試行 |

- 常駐processには`all-stops`、oneshot batchには`failures-only`が配線されている。
- 監視・通知unitはホスト全体で1組だけ登録され、テンプレートinstanceの`%i`で対象名を受け取っている。
- 通知されるのは、最初の異常から10分後も停止しているか再起動を繰り返している場合だけである。
- 導入後に、復旧した一時障害と継続する障害を別々に実地確認している。

### 秘匿値

- 正本となるホスト秘密ファイルが1本あり、アクセス権は`600`である。
- 秘匿値はunitへ`EnvironmentFile=`で渡されている。
- 正本が無い場合unitは起動に失敗し、設定漏れがその場で露出する。

## 手段

`user-unit`の各操作の使い方は`--help`が自己説明する。

| 場面 | 操作 |
|---|---|
| アプリの起動口をログアウト後も動かす | `user-unit add standing` |
| 定期実行を仕込む | `user-unit add oneshot`（serviceとtimerの2本を生成する） |
| 生成済みunitの点検・撤去・再起動 | `user-unit doctor` / `uninstall` / `restart` |
| CLIが表現できないunitを登録する | 生のunitファイルを`user-unit check` / `install`へ渡す |

`user-unit`は秘密ファイルの値を表示せず、書式と権限だけを検査する。
