# コミット規約

## このスキルの目的

コミットは、数か月後の読み手が差分だけでは分からない意図を追う手掛かりになる。
通常コミットとマージコミットの件名と本文の書き方を揃え、機械検査で規約違反を止める。

## 進め方

通常コミットとマージコミットの両方に適用する。
`commit-msg` フックが件名・必須見出し・行末の句点・文字数を検証するため、規約を外すとコミットが落ちる。

### 件名フォーマット

**通常コミット**

```
[{scope}]{type}: {日本語の概要}
```

- `{scope}`: 対象範囲。
  リポジトリ全体は[repo]、アプリ単位は[frontend]等、共有部分は[packages]/[shared]
- `{type}`: `feat` / `fix` / `refactor` / `docs` / `chore` のいずれか
- ADRファイルを追加する通常コミットは、件名末尾に`#ADR`を付ける。
  `git log --grep='#ADR'`で判断履歴を追える。

**マージコミット**

```
{branch} をマージ: {日本語の概要}
```

- `{branch}`: マージ元のブランチ名

有意義な概要は「何をしたか」を一文で書く。
終止形を基本とし、体言止めも許容する。
見出しのため句点は付けない。

### 行のルール

本文は一文を一行に収め、句点で閉じる。
折り返さない。
句点で閉じないのは件名・`#`行・空行・コードフェンス内・`|`の表行のみ。
フックが検証する。

```markdown
×
フックの出力は35,897文字で、CLIのしきい値は10,000文字、コンテキストに
入るプレビューは2,000文字だった

○
フックの出力は35,897文字で、CLIのしきい値は10,000文字、コンテキストに入るプレビューは2,000文字だった。
```

### 文体のルール

- 数か月後の読み手を対象とする。
  背景の一文目で変更前の状態を示し、指示語やリポジトリ固有の呼び名で対象を済ませない
- 箇条書きでなく散文で説明する。
  内部仕様の列挙ではなく、外部から観測できる変化を中心に書く
- 文と文は因果・順接・対比・逆接を表す接続表現でつなげる。
  背景の問題を「〜ため」「〜ことから」で方針の行動へ結び、理由は文末の「ためである」のような独立文ではなく前の文へ畳む
- 補足を文末に括弧や文片で後置しない。
  修飾は対象の直前に置き、文に溶かす
- 英単語と日本語の混在を最小限にする。
  識別子・コマンド名・固有名詞は原語
- 重要な変更に絞る。
  細部は差分が持つ
- 非公開（private）の別リポジトリは言及しない

後置修飾の例。
×禁止・△許容・○推奨。

```markdown
× `tags` パラメータを追加した（CSV、最大10件）。
△ `tags` パラメータ（CSV、最大10件）を追加した。
○ `tags` パラメータを CSV で最大10件まで受け付けるようにした。
```

理由を「〜ため」で切った文片の後置も同様に不可。
以下の○のように主文へ畳む。

```markdown
× `just clean` は生成物だけを削除する。依存関係まで消すと次の検査が遅くなるため。
○ 次の検査を遅くしないため、`just clean` は依存関係を残して生成物だけを削除する。
```

### 作成ルール

- 本文は必ず記述。
  600文字以内（フックで検証）
- 超過時は接続詞・助詞を削って帳尻を合わせず、重要度の低い情報を削る
- ドラフトを`commit-draft-{title}.md`として一時ディレクトリへ保存し、コミット後に削除

### 確認フロー

- 背景がユーザーの明言と差分から読める事実のみなら、確認せず`-F`でコミットする
- 意図を推測で補った場合は、コミット前に要点を提示して確認する

### 本文構成

差分に無い情報のみを載せる。
種別ごとの見出しをこの順で置く。

**通常コミット**

1. `## 背景`: 観測した事実と動機
2. `## 方針`: 解法・理由・退けた案（足し引きの列挙は差分が持つ）
3. `## 効果・影響`: 利用者が観測する体験・振る舞いの変化を書く。
   差分やテスト・CIの備考から読み取れる実装の細部は書かない（変わらないことも）

`効果・影響` の書き分け。

```markdown
× h2 は番号・本文・罫線・ボタンの順に並び、ボタンは画面幅に関わらず右端に揃う。見出しから段落までのすき間は 14px から 24px へ広がった。描画テストの期待値を更新し、CI は通過している。
○ リンクボタンが番号と本文の間を挟まなくなり、見出しを読む際の流れが分断されなくなった。見出しと内容の間隔が広がり、節の区切りが読み取りやすくなった。
```

**マージコミット**

書き方は通常コミットと同じ文体・作成ルールに従う。
見出しは次の3節。

1. `## サマリー`: マージの目的と到達状態
2. `## 含まれる変更`: 変更を振る舞いの単位で挙げる
3. `## 残課題`: マージ後に残る作業

### 例（通常コミット）

```markdown
[api]fix: リクエストボディをzodで検証し、不正な入力を400で拒否する

## 背景

これまで `POST /todos` はリクエストボディを型アサーションで信頼して処理しており、`title` の欠落や空文字でもそのまま保存できてしまっていた。
ただし入力チェックはフロント側にしかなく、APIを直接叩くクライアントからは素通りする状態だった。

## 方針

不正な入力を拒否するため、リクエストボディは zod のスキーマで検証し、違反時は Detail 付きの 400 を返すようにした。
バリデーションを各ハンドラに散らすと重複するため、`createTodo` の入口でひとまとめにした。

## 効果・影響

`POST /todos` は `title` の欠落や空文字を 400 Bad Request で拒否し、不正データは DB に到達しなくなった。
正常なリクエストは従来と同じレスポンスを返すため、フロント側の変更は不要。
```
