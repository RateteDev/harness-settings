# リリース手順と方針

変更のまとまりごとにバージョンを更新し、GitタグおよびGitHub Releaseを作成する。

## 1. バージョンとタグの管理

- **バージョン番号の一貫性**: プロジェクトのマニフェストファイル（`package.json` や `.csproj` など）のバージョンを正とし、リリースのたびに更新する。
- **タグの形式**: 対象コミットに対し、`v{version}` 形式の注釈付き（annotated）タグを作成する。
- **READMEの記載**: インストールコマンドにバージョンやタグを含めない（パッケージマネージャーの互換性維持および更新漏れ防止のため）。

## 2. リリースノートの作成

コミットログの羅列ではなく、**利用者が「自分に影響する変化」を一目で把握できる内容**にする。

### 基本方針
- **視点**: 内部実装ではなく、外部から観測できる変化を書く。
- **言語**: 日本語（リポジトリの主要言語が異なる場合はそれに合わせる）。
- **トーン**: 親しみやすく遊び心のあるトーン（Discordのリリースノートなどを意識）。
- **対象読者**: リポジトリの内部構造を知らない利用者。

### 記載する内容・除外する内容
- **記載する**:
  - 新機能、利便性の向上
  - 不具合修正、セキュリティ修正
  - 利用者に影響のある依存関係の更新
  - 破壊的変更（設定や使い方の変更が必要なもの）
- **記載しない（除外）**:
  - 内部リファクタリング、テストの追加・更新、ドキュメント修正、アセット変更など、利用者の操作に影響しない変更。

### 構成フォーマット

```markdown
『{遊び心のある短いサブタイトル}』をリリース！

{このバージョンの要点を伝える導入文}
{必要に応じて、セキュリティ修正や破壊的変更への注意喚起を1〜2行で記載}

### 🎉 新機能
- {新しくできるようになったこと、改善された点を1文で記載}

### 🐛 不具合修正
- {修正された不具合やセキュリティ対応を1文で記載}

### ⚠️ 破壊的変更
- {ユーザー側で対応が必要な変更（機能削除、デフォルト値変更、推奨環境の変更など）を1文で記載}
```

※ 該当する項目がない見出し（H3）は省略する。  
※ 各項目はリンクがなくても意味が通じる1文で記述する（関連コミット・Issueへのリンクは任意）。  
※ GitHubの自動生成ノートは下書きとしての参照にとどめ、そのまま流用しないこと。

## 3. 作成後の確認

作成後は [output-example.md](output-example.md) と見比べ、トーンや構成に不足がないか確認して仕上げる。
