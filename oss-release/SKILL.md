# OSS公開

リポジトリをOSSとして公開する作業である。公開前チェック、READMEの確認、公開操作、リリースをこの順で行う。

## 公開前チェック

次の3つを順に行い、未解消の項目が残る間は公開しない。

### 秘密情報・端末情報

現行ファイルとGit履歴（削除済みファイルを含む）に、秘密情報・個人情報・端末固有情報が無いことを確認する。履歴を作り直す場合はこの確認をスキップできる。
検出したときは、値そのものを出力せず、場所と種類だけを報告する。

### 権利関係

公開対象のコード・素材・依存物を公開・再配布できることを確認する。実施者はユーザーである。

### 再現性

クリーンなPodmanコンテナで、READMEの導入から実行までを全行程省略せず実行する。

## README

公開するリポジトリには、初見の人が何のためのものか、どう試せるかを把握できるREADMEを用意する。

- 本文の既定言語は日本語とし、ユーザーから指定があった場合だけ別の言語で書く。
- 冒頭で用途と対象を簡潔に伝え、前提・導入・最小の実行例へつなぐ。コマンドと動作は対象リポジトリで確認する。
- 機能や導入経路が複数あるときは最短の入口を示し、詳しい説明は既存の文書へリンクする。見出しや機能一覧を増やすこと自体を目的にしない。
- 性質の違う導線（例：ライブラリの導入と同梱スキルの配置）は別の節に分ける。
- コマンド例では各コマンド行の直前に、その行で何が起きるかを短く書く。結果を補足するときは同じコメントの括弧内に収める。
- 図は画像で示し、Mermaidは使わない。操作の流れを示すときは、実際の入力・操作・出力が追える具体的な画面や成果物を描き、その表記をソースに照らして確認する。本文か代替テキストからも流れが分かるようにする。
- 公開前にライセンスを決めてライセンスファイルを用意し、READMEのライセンス欄から実際の条件へリンクする。ライセンスが未決定なら公開前にユーザーへ確認する。
- ライセンスは上部バッジで状態を示し、下部の見出し付きリンクから条件へ案内する。
- バッジは実際の配布先や状態を表すものにし、文言は公開前にユーザーの確認を得る。
- 言語リンクやバッジが複数あるときは1行に2件ずつ並べ、狭い画面で崩れないか確認する。
- 言語版を用意する場合は `docs/readme/` に置き、既定言語版をリポジトリのルートに残す。GitHubは `.github/`・ルート・`docs/` の直下にあるREADMEだけをリポジトリの顔として表示するためである。

## 公開

公開前チェックの3項目とREADMEの確認が終わり、ライセンスとバッジの文言をユーザーが承認したらpublic化する。

### 公開操作

可視性をpublicへ切り替える。

```sh
gh repo edit <owner>/<repo> --visibility public --accept-visibility-change-consequences
```

履歴から秘密情報・端末情報を除く必要があった場合は、force-pushではGitHub側の古いオブジェクトがSHA直指定で到達できる期間が残るため、リポジトリを削除して同じ名前で作り直し、`main`をpushする。削除ではstar・fork・issue・release・設定が失われるため、事前に失うものを確認し、控えを取るかはユーザーが決める。公開後に履歴を書き換えると他者のcloneが壊れるため行わない。

### 公開後の確認

- 可視性・既定ブランチ・issuesやwikiの設定が意図どおりか確認する。
- 認証なしでGitHubから導入できることを確認する。`github:`参照の導入はpublicでなければ通らないため、公開後に実行する。
- クリーンなPodmanコンテナでREADMEの導入から実行までを通しで行い、全行程が再現することを確認する。

対話認証や実アカウントを要する手順はエージェントが実行できないため、ユーザーが代わりに行う。エージェントは手前までを確認し、未確認の範囲を報告する。

## リリース

公開後は、変更のまとまりごとに版を切り、タグとGitHub Releaseを作る。

- 版数は`package.json`の`version`を唯一の正とし、リリースのたびに上げる。
- タグは`v{version}`の注釈付きタグとし、リリース対象のcommitを指す。
- リリース本文はrelease-note-conventionスキルに従う。
- 利用側の`github:`参照は、再現性のため`main`ではなくタグを推奨する。READMEの導入手順をこの形に保つ。

## Pages

作らない。ライブラリとCLIの説明はREADMEと同梱スキルで足り、Pagesで公開する追加のコンテンツが無いためである。ドキュメントサイトを持つ必要が出た時点で規則を定める。
