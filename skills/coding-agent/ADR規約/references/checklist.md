# ADRレビュー

作成者以外のエージェントが、対象のADR（Architecture Decision Record）を検証するためのチェックリストです。ファイルの修正は行わず検証結果のみを出力してください。

## 実行ルール

1. 対象ADRを読みすべてのチェック項目を判定する。
2. **ファイルの編集は行わない**（修正は作成者に委ねる）。
3. 指摘事項と、判断内容そのものへの異議（議論すべき論点）は分けて出力する。
4. 問題がない場合は「**指摘事項はありません。**」とだけ出力する。

## 出力フォーマット

問題がある場合は以下の形式で出力してください。

```markdown
### 指摘事項
- **[該当項目名]**
  - 指摘箇所: （該当の行やテキストを引用）
  - 修正案: （具体的な直し方）

### 作成者へ伝えるべき論点（※判断内容そのものに異議がある場合のみ）
- （議論が必要なポイント）
```

---

## チェックリスト

### 1. 対象の妥当性
- [ ] 複数の選択肢を比較検討した結果である（不採用の選択肢が明記されている）。
  - ※不採用案がない場合は「ADRの対象外」と指摘する。
- [ ] 採用理由を裏付ける調査・検証結果が`根拠`に書かれている。

### 2. ファイル名と構成
- [ ] ファイル名が `YYYYMMDD-hhmm-{h1タイトル}.md` の形式で、タイトル部分がh1と完全一致している。
- [ ] **h1**: タイトル1つのみ。バッククォート（` `）・半角空白・スラッシュ（`/`）を含まない。
- [ ] **h2**: `背景` と `判断` の2つのみ。
- [ ] **h3**: `判断` の配下に、判断事項ごとに設置されている。
- [ ] **本文**: frontmatterや不要な日付（調査日時のタイムスタンプ等を除く）が含まれていない。

### 3. 内容と記述量
- [ ] `背景`: 「課題・経緯・検討理由」が2〜4文で簡潔にまとまっている。
- [ ] `判断`（各h3配下）: 
  - 直下の冒頭1〜2文で「採用・見送り・保留」の結論が明記されている。
  - 構成が「本文 → `**根拠**`」の順になっている。
  - `根拠`には判断の決め手のみが書かれ、背景の再説明になっていない。
- [ ] 決定済みの設計方針のみを扱い、予定・未決定の論点・無関係な設計を含まない。
- [ ] 実装詳細（関数名・定数名など）に依存せず、設計レベルの言葉で記述されている（識別子そのものの決定を除く）。
- [ ] 同じ事実や数値を重複して記述していない。

### 4. 文章表現
- [ ] 常体（である調）で統一されている。
- [ ] 判断の根拠となる数値や固有名詞（バージョン・計測値・ライブラリ名など）が具体的である。
- [ ] 1文ごとの長さと構造:
  - 地の文: 1文 **100字以内**（対象・理由・手段を明確にして因果関係を示す）。
  - 箇条書き: 1項目 **80字以内**、読点（）は **2つまで**。

### 5. 図表
- [ ] 比較や一覧は「表（テーブル）」に、注意・制約・リスクは「注記」にまとめられている。
- [ ] 構造・関係・フローを説明する場合、文章より先にMermaid図で図示されている。
