# コミットメッセージ

通常コミットとマージコミットの両方に適用する。件名フォーマットと本文構成のみ種別ごとに異なり、その他のルールは共通とする。

`commit-msg` フックが件名・必須見出し・行末の句点・文字数を機械検証するため、規約を外すとコミットが落ちる。

## 件名フォーマット

### 通常コミット

```
[{scope}]{type}: {日本語の概要}
```

- `{scope}`: 変更対象範囲を表現する。モノレポ構成を前提とする。
    - レポジトリ全体にまたがる場合には[repo]、特定のアプリケーション内に閉じた変更であればそれを使用する。例: [frontend], [android]
    - アプリケーションが共有で使用する部分に閉じた変更には、そのリポジトリの共有ディレクトリ名を使用する。例: [packages], [shared]
- `{type}`: `feat` / `fix` / `refactor` / `docs` / `chore` のいずれかを使用する。これら以外は使用しない

### マージコミット

```
{branch} をマージ: {日本語の概要}
```

- `{branch}`: マージ元のブランチ名

いずれの種別も `{日本語の概要}` は「何をしたか」を一文で書く。終止形を基本とし、体言止めも許容する。見出しであるため句点は付けない。

ADRファイルを追加するコミットは、件名末尾に`#ADR`を付ける。`git log --grep='#ADR'`で設計判断の履歴を追える形にする。

## 行のルール

件名と `##` 見出しは句点なしで書く。それ以外の本文の行は、散文も箇条書きも、一文を一行に収めて句点（。）で閉じる。文字数による途中折り返しは行わない。

句点で閉じない行は、件名・`#` で始まる行・空行・コードフェンスの内側・`|` で始まる表の行に限る。`commit-msg` フックがこれを機械検証する。

```markdown
×
フックの出力は35,897文字で、CLIの永続化しきい値は10,000文字、コンテキストに
入るプレビューは2,000文字だった

○
フックの出力は35,897文字で、CLIの永続化しきい値は10,000文字、コンテキストに入るプレビューは2,000文字だった。
```

## 文体のルール

- 読み手は、数か月後に履歴を振り返る人とする。背景の一文目で変更前の状態を示し、「両方」「それ」のような指示語や、リポジトリ固有の呼び名だけで対象を済ませない
- 背景は無機質な箇条書きで済ませず、散文で読みやすく説明する
- 内部仕様の詳細（ファイルパス、関数名、アルゴリズムの実装手順など）の列挙ではなく、外部から観測できる振る舞いや呼び出し方法の変化を中心に記述する
- 散文部では英単語と日本語の混在を最小限にする。識別子・コマンド名・固有名詞は原語のまま残し、一般語は日本語へ置き換える（例: ×「attach させる」 ◯「接続させる」）
- すべての変更を網羅しようとせず、重要な変更のみに焦点を絞り簡潔にまとめる
- 細部は差分から読み取れるため、本文では多少抽象化してでもアーキテクチャの変更点や処理フローの全体像を読み手に伝えることを優先する
- 補足を文末に括弧や文片で後置しない。修飾は対象の語の直後に置き、できる限り文に溶かす
- 非公開（private）の別リポジトリは、読者が参照を確認できず情報として意味を持たないため言及しない。OSSなど公開されている参照先であれば言及してよい
- 文と文は因果・順接・対比・逆接を表す接続表現でつなげる。背景で見た問題を「〜ため」「〜ことから」で方針の行動へ結び、理由は文末の「ためである」のような独立文ではなく前の文へ畳む。独立した短い断定文を並べて文を閉じるのを避ける

後置修飾の例。上から順に、禁止・許容・推奨とする。

```markdown
×
`tags` パラメータを追加した（CSV、最大10件）。

△
`tags` パラメータ（CSV、最大10件）を追加した。

○
`tags` パラメータを CSV で最大10件まで受け付けるようにした。
```

理由だけを「〜ため」で切った文片を後ろに置くのも後置修飾にあたる。一文に畳むか、独立した文にする。

```markdown
×
`just restart` はプロセスを起動せず systemd に委ねる。
レシピ側でも起動するとユニットの自動再起動と競合するため。

○
レシピ側でも起動するとユニットの自動再起動と競合するため、`just restart` はプロセスを起動せず systemd に委ねる。
```

## 作成ルール

- 本文は必ず記述
- 600文字以内に収める（`commit-msg` フックで機械的に検証される）
- 文字数超過の際は、接続詞・助詞の削減や単語の言い換え・修飾語の削除といった小手先の調整で帳尻を合わせず、重要度の低い情報そのものを削るか文単位で抽象化して対処する
- 完成したコミットメッセージはドラフトとしてユーザー指定の一時ディレクトリに`commit-draft-{commit title}.md`の形式で保存する
- コミット後ドラフトファイルを削除する

## 確認フロー

- 本文冒頭節（通常コミットの`## 背景`、マージコミットの`## サマリー`）の内容が、会話でユーザーが明言した理由や差分から機械的に読み取れる事実のみで構成できる場合、確認を取らずそのまま`-F`オプションでコミットまで完了させる
- 意図・目的・経緯についてユーザーが明言していない部分を推測で補って記述した場合は、コミット前に要点を対話上で簡潔に提示し、確認を取ってから進める。ドラフト全文やファイルを開いての確認は求めない
- 明確か推測かの判断に迷う場合は、確認を取る側に倒す

## 本文構成

本文は種別に応じた以下の3節を、この順序で必ず配置する。各節は差分に無い情報を載せるためにある。差分から読み取れることを書き写す節は一つもない。

### 通常コミット

1. `## 背景`: 観測した事実と、変更に至った動機を書く
2. `## 方針`: どう解いたか、なぜその形にしたか、退けた案は何かを書く。何を足し何を消したかの列挙は差分が持っているため書かない
3. `## 効果・影響`: 運用者・利用者・次に設計する人から見て、変更の前後で何が変わるかを書く。変わらないことも書く

### マージコミット

本文の書き方は通常コミットと同じ文体・作成ルールに従う。見出しは次の3節を順に置く。

1. `## サマリー`: マージの目的と、これによって到達した状態を書く
2. `## 含まれる変更`: 含まれる変更を観測できる振る舞いの単位で挙げる
3. `## 残課題`: マージ後に残る作業を書く

## 例

### 通常コミット

```markdown
[api]fix: リクエストボディをzodで検証し、不正な入力を400で拒否する

## 背景

これまで `POST /todos` はリクエストボディを型アサーションで信頼して処理しており、`title` の欠落や空文字でもそのまま保存できてしまっていた。
ただし入力チェックはフロント側にしかなく、APIを直接叩くクライアントからは素通りする状態だった。

## 方針

不正な入力を拒否するため、リクエストボディは zod のスキーマで検証し、違反時は Detail 付きの 400 を返すようにした。
バリデーションを各ハンドラに散らすと重複するため、`createTodo` の入口でひとまとめにした。

## 効果・影響

`POST /todos` は `title` の欠落や空文字を 400 Bad Request で拒否し、不正データは DB に到達しなくなった。
正常なリクエストは従来と同じレスポンスを返すため、フロント側の変更は不要。
```
