# リポジトリ監査

機械検査だけでは判断できない内容を確認する。`scripts/audit.sh`の終了statusにかかわらず、この文書にある現在の全項目を実施する。

推測で埋めず、対象ファイルを読んで判断する。機械検査の`FAIL`・`WARN`とエージェント検査の指摘を一つの表へまとめ、対処の要否と根拠を添えて報告する。問題は無断で修正しない。

## エージェント検査

### リポジトリ構成

- ディレクトリと入口文書が実際のアプリケーション・共有package・infra構成を表しているか。
- 空の雛形、使われない設定、存在しない対象を指す説明が残っていないか。
- `AGENTS.md`、README、CONTRIBUTING、ADR、仕様書の責務が重複していないか。

### AGENTS.md

- 記載内容が現在の構成と運用に一致しているか。
- 常時必要な制約だけがあり、特定作業の手順やコードから導出できる説明が混ざっていないか。
- より限定された範囲の`AGENTS.md`と責務が重複していないか。

### justfile

- recipe名がリポジトリの実構成と対応しているか。
- `just --list`の説明がrecipeの実際の動作を説明しているか。
- `check`がファイルを書き換えず、`fix`と対になっているか。
- 非公開recipeに`[private]`と`_`接頭辞があり、groupと引数のdefaultが実態に合うか。
- recipeの中身が空、`@echo`だけ、存在しないcommandやpathを指す状態になっていないか。
- `repo-checks`がそのリポジトリ固有の横断的不変条件を検査しているか。

### Git hooks

- pre-commitのpath条件が実在するディレクトリと一致しているか。
- commit-msgが現在のcommit規約と一致しているか。
- hookがjustfileやCIと同じ検査を別実装として重複させていないか。

### ローカル検査とリモートCI

- jobが独立して実行できる単位へ分かれているか。
- `repo-checks`がローカルとリモートの両方から同じrecipeとして呼ばれるか。
- lockfileのhashを鍵とした依存cacheがあるか。
- `ci-local`とremote CIの検査内容が乖離していないか。
- timeoutとconcurrencyが実際のjob構成に合うか。

### ツールチェーン

- `mise.toml`の宣言が実際に使うtoolと過不足なく一致しているか。
- versionが他の設定へ重複していないか。
- lockfileとinstallerが複数のpackage managerを誤って併用していないか。

### 規約と実効性

- templateから配置されたファイルが存在するだけでなく、実際の開発フローで呼ばれているか。
- checkを迂回する別経路や、古いtool・旧運用への参照が残っていないか。
- 検査対象外にした例外に具体的な理由があるか。

## 報告

重要度の高い順に、対象、機械検査またはエージェント検査の区分、問題、対処案を表で示す。問題が無い場合も、機械検査とエージェント検査の両方を完了したことを明記する。
