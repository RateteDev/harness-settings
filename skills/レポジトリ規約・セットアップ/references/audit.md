# リポジトリ監査

機械検査だけでは判断できない内容を、エージェントが確認するための手引きである。
`scripts/audit.sh`の終了statusにかかわらず、この文書にある全項目を確認する。
各項目は成り立つべき状態であり、成り立たない項目を指摘として報告する。

## 確認の仕方

- 各項目は、推測で埋めず、対象ファイルを読んで判定する。
- 指摘は報告だけにとどめ、修正はユーザーから新しい`GO`を得てから行う。
  監査は現状の報告であり、修正の承認を含まないためである。

## エージェント検査

### リポジトリ構成

- ディレクトリと入口文書が、実際のアプリケーション・共有package・infra構成を表している。
- 空の雛形、使われない設定、存在しない対象を指す説明が残っていない。
- `AGENTS.md`、README、CONTRIBUTING、ADR、仕様書の責務が分かれている。

### AGENTS.md

- 記載内容が現在の構成と運用に一致している。
- 常時必要な制約だけがあり、特定作業の手順やコードから導出できる説明は別の場所にある。
- より限定された範囲の`AGENTS.md`と責務が分かれている。

### justfile

- recipe名がリポジトリの実構成と対応している。
- `just --list`の説明がrecipeの実際の動作を表している。
- `check`はファイルを書き換えず、`fix`と対になっている。
- 非公開recipeは`[private]`と`_`接頭辞を持ち、groupと引数のdefaultが実態に合っている。
- recipeの中身が実際の処理を持ち、空、`@echo`だけ、存在しないcommandやpathを指す状態になっていない。
- `repo-checks`が、そのリポジトリ固有の横断的不変条件を検査している。

### Git hooks

- `pre-commit`のpath条件が実在するディレクトリと一致している。
- `commit-msg`が現在のcommit規約と一致している。
- hookはjustfileやCIの検査をrecipe経由で呼び、同じ検査を別実装として持っていない。

### ローカル検査とリモートCI

- jobが独立して実行できる単位へ分かれている。
- `repo-checks`がローカルとリモートの両方から同じrecipeとして呼ばれている。
- lockfileのhashを鍵とした依存cacheがある。
- `ci-local`とリモートCIの検査内容が一致している。
- timeoutとconcurrencyが実際のjob構成に合っている。

### ツールチェーン

- `mise.toml`の宣言が、実際に使うtoolと過不足なく一致している。
- versionは`mise.toml`だけにあり、他の設定に重複していない。
- lockfileとinstallerが一つのpackage managerにそろっている。

### 規約の実効性

- 雛形から配置されたファイルが、存在するだけでなく実際の開発フローで呼ばれている。
- checkを迂回する別経路や、古いtool・旧運用への参照が残っていない。
- 検査対象外にした例外には、具体的な理由が書かれている。

## 報告

- 機械検査の`FAIL`・`WARN`とエージェント検査の指摘が、一つの表にまとまっている。
- 表は重要度の高い順に、重要度、区分（機械検査・エージェント検査）、対象、問題、対処案と要否の根拠を示す。
- 問題が無い場合も、機械検査とエージェント検査の両方を完了したことが明記されている。
