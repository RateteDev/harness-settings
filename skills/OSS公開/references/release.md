# リリース手順

機能追加や修正などの区切りごとに、バージョン更新・タグ付け・GitHub Releaseの作成を行います。

## 1. バージョンとタグ

- **バージョンの更新**: リリースのたびに、マニフェストファイル（`package.json`の`version`、`.csproj`の`Version`など）のバージョンを上げます（この値を正とします）。
- **タグの作成**: リリース対象のコミットに対し、`v{version}` の形式で注釈付きタグ（annotated tag）を作成します。
- **READMEの記載**: インストールコマンドにはバージョンやタグを含めないでください（固定したい利用者は各自で指定できるため、READMEの更新頻度を抑えます）。

## 2. リリースノート作成ルール

コミットログをそのまま並べるのではなく、**「利用者が自分に関係する変化をすぐ把握できること」**を目的に書きます。

- **対象読者**: リポジトリの内部構造を知らない利用者
- **言語**: 日本語（リポジトリ側の既定言語が別にある場合はそれに合わせる）
- **対象差分**: 前回タグから `HEAD` まで
- **記載するもの**:
  - 外から観測できる機能や挙動の変化
  - 利用者に影響がある依存関係の更新
- **記載しないもの**:
  - 内部リファクタリング、テスト、内部ドキュメント、アセット変更など（利用者の行動に影響しないもの）
- **コミットログの扱い**:
  - コミットの件名や本文をそのまま貼らない（GitHubの自動生成は下書きとしてのみ使用）

### フォーマットと構成

該当する項目がない見出しは省略してください。各項目は1文で、コミット等へのリンクがなくても意味が通るように記述します。

```markdown
『{サブタイトル}』をリリース！

{そのバージョンの要点を伝える導入文。少し遊び心のある親しみやすいトーンで書く}
{破壊的変更や重要なセキュリティ修正がある場合のみ、ここで注意を促す}

### 🎉 新機能
- {新しくできるようになったこと、改善されて扱いやすくなったこと}

### 🐛 不具合修正
- {修正された不具合、セキュリティ問題の解決}

### ⚠️ 破壊的変更
- {機能削除、既定値変更、対応環境の変更など、利用側で対応が必要な変更}
```
