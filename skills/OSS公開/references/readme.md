# README

公開するリポジトリのREADMEは、初見の人が何のためのものか、どう試せるかを把握できる状態にする。

## 構成

- タイトルの直後に用途と対象を一文で書き、前提・導入・最小の実行例へつなげる。
- できることは絵文字付きの箇条書きで並べる。
  書いたコマンドと動作は、対象リポジトリで確認する。
- 利用者が最初に読む節は短い段落と箇条書きで構成し、1段落は2文までにする。
- 機能や導入経路が複数あるときは最短の入口だけを示し、詳しい説明は既存の文書へのリンクにする。
  見出しや機能一覧は、利用者が試すのに要る分だけ置く。
- 入手と利用を分け、「インストール」「使い方」の順に節を置く。
- 性質の違う導線（例：ライブラリの導入と同梱スキルの配置）は別の節に分ける。
- リポジトリの目的が完成品の配布なら、開発節は置かず、ビルドやテストの手順はソースや別文書に置く。
- 利用者に影響する注意点は「注意点」の見出しに短くまとめる。
  書くのは対応外の形式と自動で止まる条件だけで、内部の上限値は列挙しない。
- コマンド例では、各コマンド行の直前にその行で何が起きるかを短く書く。
  結果の補足は同じコメントの括弧内に収める。

## 図と画像

- 図は画像で示し、Mermaidは使わない。
- 操作の流れを示す図は、実際の入力・操作・出力が追える具体的な画面や成果物を描き、その表記をソースと一致させる。
- 図の流れは、本文か代替テキストからも分かるようにする。
- GUIや視覚的な操作があるアプリでは、実画面のスクリーンショットを置く。
  画像を用意できない場合はユーザーへ依頼し、READMEは実在する画像だけを参照する。

## ヒーロー

- ヒーローは中央寄せにし、ワードマーク・バッジ・言語リンクの順に並べる。
- ワードマークは、文字をアウトライン化したSVGを`assets/`に置き、`<picture>`でlight/darkを出し分ける。
  環境のフォントに表示を左右させないためである。
- バッジは実際の配布先や状態を表すものにし、文言は公開前にユーザーの確認を得る。
- 言語リンクやバッジが複数あるときは1行に2件ずつ並べ、狭い画面でも崩れないことを確かめる。

## ライセンス

- ライセンスは公開前に確定させ、ライセンスファイルを置く。
  未決定なら公開前にユーザーへ確認する。
- ライセンスは上部のバッジで状態を示し、下部の「ライセンス」見出しのリンクから実際の条件へ案内する。

## 多言語

- 既定言語版はリポジトリのルートの`README.md`に、英語版は`docs/readme/README.en.md`に置く。
  GitHubは`.github/`・ルート・`docs/`の直下にあるREADMEだけをリポジトリの顔として表示するためである。
- 双方の先頭に`{既定言語} ・ English`の言語リンクを並べる。

## 仕上がり

- GitHubのmarkdownレンダリングでの表示か画像への描き出しで、レイアウトが崩れないことを確かめる。
- [見本](output-example.md)と並べて写す観点を点検し、届かない観点は直す。
- プラットフォーム差などで写せない観点は、残課題としてユーザーへ伝える。
