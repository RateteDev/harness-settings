# OSS公開

## 目的

一度公開した情報は完全な取り消しが困難です。
情報漏洩や権利侵害、再現性の不備を防ぐため事前検証とドキュメント整備を完了した状態で安全にリポジトリを公開します。

## チェック要件（あるべき状態）

### 1. 機密情報・環境情報の排除
- 現在のファイルおよびGitの全履歴に、機密情報（トークン・鍵など）・個人情報・環境固有情報（ローカルパスなど）が含まれていないこと。
- `scripts/audit.sh <repo>` で機械的検証を行う（履歴を作り直して公開する場合は履歴チェックを省略可）。
- **機密情報検出時の報告ルール**: 値そのものは出力せず、**場所と種類のみ**を報告する。

### 2. 権利関係のクリア
- 公開対象のコード・画像等の素材・依存ライブラリが、ライセンス上公開および再配布可能であることをユーザーが確認していること。

### 3. 再現性の検証
- クリーンな Podman コンテナ環境で、READMEに記載の手順（導入〜実行）を省略なく通せること。
- プライベート時の `github:` 依存解決は認証エラーになるため、事前検証時はローカルパス参照に差し替えて確認する。
- 対話的認証・実アカウント・実機が必要な手順は、手順書を整理した上でユーザーに検証を依頼する。

### 4. README・リリースノート
- 原則として**日本語**で記述する（ユーザーから言語の指定がある場合を除く）。
- ドキュメント作成・修正時は以下を参照する:
  - READMEの規則: [README](references/readme.md)
  - バージョン・タグ・リリースノートの規則: [リリース](references/release.md)
  - 構成・品質基準の比較: [見本](references/output-example.md)
- 見本の基準を満たせない項目がある場合は理由を添えて残課題としてユーザーへ報告する。

### 5. 公開設定
- 履歴から機密情報を完全に消去して公開する場合は**リポジトリを削除して同名で再作成し、`main` のみをpushする**（※force-pushでは古いコミットオブジェクトがGitHub上に残るため）。
- 公開後は他者のクローンを破壊するため、**Git履歴の改変（force-push等）を行わない**。
- 公開完了後、以下を確認する:
  - リポジトリの可視性（Public）・既定ブランチ・Issues・Wikiの有効状態
  - 未認証環境から `github:` 参照のまま導入・実行できること

## 実行手順

1. **未定義作業の確認**
   - 本手順にない作業（例: GitHub Pages公開など）を依頼された場合は、作業前に本規約（`references/` 等）へルールを追記・定義する。
2. **事前検証とドキュメント作成**
   - 機密情報チェック・権利確認・再現性検証・README作成を実施し、未解決課題をゼロにする。
3. **ユーザー承認の取得**
   - 適用ライセンスとバッジの文言についてユーザーの承認を得る。
   - 履歴再作成（リポジトリ再作成）を行う場合は、失われる情報（Star, Fork, Issue, Release, 設定）を提示し、バックアップ要否と続行の合意を得る。
4. **公開の実施**
   - コマンドを実行してリポジトリをパブリック化する。
5. **公開後の動作確認**
   - 設定値および未認証環境からの導入可否を確認する。
6. **初回リリースの作成**
   - タグ打ちとGitHub Releaseの発行を行う。

## コマンド・ツール仕様

- **パブリック化コマンド**:
  ```sh
  gh repo edit <owner>/<repo> --visibility public --accept-visibility-change-consequences
  ```

- **監査スクリプト**:
  ```sh
  scripts/audit.sh <repo>
  ```
  - ファイル・コミット履歴・コミット作成者を検査する。
  - 問題検出時は該当の「種類」と「場所」のみを出力し終了コード `1` で終了する。
